## 1. 先解决一个没人处理过的问题：五条子序列没有共同的时间线

五份设计文档各自给了实施顺序，彼此都合理，但**从未被排到一条线上**：

| 序列 | 出处 | 内容 |
|---|---|---|
| **B0–B7** | `ARCHITECTURE.md` §9 | 骨架 → 身份 → 目录 → 数据平面 → 路由 → 计费 → 管理端 → 私有化 |
| **P1–P7** | `UNIFIED-PROVIDER-INTERFACE.md` §10 | IR → openai 兼容 → 协商与路由 → anthropic → gemini → 多模态 → 异步任务 |
| **M1–M7** | `BILLING-AND-PRICING.md` §10 | 价目 → 成本售价拆分 → 预扣结算 → 对账 → credits → 账单 → 毛利 |
| **G0–G7** | `SELF-HOSTED-GPU-OPERATIONS.md` §9 | 数据模型 → 检测/指标/记账 → 权重 → 生命周期 → 入路由 → 成本 → 预排程与扩缩 → 压测 |
| **S0–S4** | `SERVICE-DECOMPOSITION.md` §10 | 模块化纪律 → 装配层 → 拆 Gateway → 拆 Worker → 拆 Infra Agent |

> **G 序列于 2026-09-09 重新拆分**：原 `G1` 被拆成 `G0`（数据模型）/ `G1a`（设备检测）/
> `G1b`（指标）/ `G1c`（记账对账），`G6` 拆成 cron 预排程与预测性扩缩容两档。
> 依据是对 GPUStack 及其硬件抽象层的源码复核（见 §3-I7）。

三处冲突必须裁决，否则实现时会撞车：

**① `B5` 与 `M1–M7` 不是同一颗粒度。** B5 一行"计量计费"，M 序列把它拆成七步，且 **M1/M2 必须紧跟 B3，不能等到 B5**——`request_logs` 的字段形状一旦有生产数据就要迁移（计价方案 §10 已论证）。本文据此把 M1/M2 前移。

**② `G5` 与 `M7` 是同一件事的两半。** G5「成本核算与摊销回填」与 M7「毛利视图 + 自建摊销回填」重叠。**裁决：M7 是真相源（它定义字段与不可变约束），G5 是它在 GPU 侧的数据来源（利用率与摊销公式）**，两者同一迭代交付，不拆开。

**③ `S0/S1` 没有前置条件，却决定后面所有代码的形状。** 模块边界纪律与拓扑装配层若不在第一个迭代立好，后面每写一行都在增加将来的返工量。**它们必须在 I0，且不产生任何分布式系统成本**（`SERVICE-DECOMPOSITION.md` §10 已论证）。

另有八项跨领域任务不属于任何序列，此前无人认领，本文记为 **X 系列**。

## 2. 排期原则

1. **风险前置。** 流式转发、预扣结算、协议转换是三处技术风险最高的地方，都排在前半程。先做完一堆 CRUD 再发现流式有坑，代价高一个数量级。
2. **不可逆的先做。** 数据模型（尤其 `request_logs`、`model_prices`）一旦有生产数据，改动成本从"改代码"变成"数据迁移 + 历史重算"。
3. **零成本的纪律先立。** S0/S1、CI 依赖检查、测试基建不引入任何运行时复杂度，却保留全部未来选项。
4. **契约先于实现。** 每个迭代开始前，该迭代涉及的端点契约必须先落到 yaml，前后端同时开工。
5. **每个迭代都能演示。** 判据一律是可观察的行为，不是"代码写完了"。

**人力假设**：2–3 名后端。若只有 1 人，迭代内的并行任务串行化，周数约 ×1.8。**周数是相对规模的量纲，不是承诺**。

### I3 · 数据平面 MVP（约 3 周）· **最高风险** · ✅ **已完成（2026-09-11）**

> **交付**：`POST /v1/chat/completions`（含流式）单渠道直连可用；两段流式
> 超时（首字节/stall）用一个可重置定时器实现；客户端断开会通过派生的
> context 自动取消上游请求；`request_logs` 按 attempt 级记录写入
> （异步 channel + `pgx.CopyFrom` 批量落库）。单测（含用真实 fake 上游
> 服务器的集成测试）+ 对真实 Postgres 的手工验证全通过；`make ci` 全绿。
>
> **风险前置验证点已演示**：上游首字节前失败 → 干净的 OpenAI 形状错误
> 响应（还没写过任何字节）；首字节后失败（stall 超时/客户端断开）→
> 一个 `EventError` SSE 事件 + `[DONE]`，**绝不补一个假的
> `finish_reason: stop`**——`TestCompletions_StallTimeoutAfterFirstByte`
> 与 `TestCompletions_ClientDisconnectCancelsUpstream` 把这两条钉成了
> 可重复运行的回归测试，不是靠代码评审保证。
>
> **两个抓到的真问题**：
> 1. **watchdog 的两个布尔量最初不是原子的**——定时器触发回调运行在
>    独立 goroutine，与主 goroutine 的读循环天然并发，`go test -race`
>    当场标红。这不是可以靠"调用顺序"绕开的竞态，是这个类型存在的
>    意义本身（提前打断一个正在阻塞的调用），因此改成 `atomic.Bool`。
> 2. **`gateway.ValidateGateway` 起初被塞进通用的 `Config.Validate()`**，
>    导致 `umaas-migrate`、`umaas seed`、`umaas admin create` 全部因为
>    "没配置上游"而拒绝启动——这几个工具根本不碰数据平面。教训是：
>    校验要挂在"谁真的需要它"上，不能因为方便就塞进一个所有二进制
>    共用的入口。现已拆成独立方法，只在真正装配数据平面路由前调用。
>
> **顺带修了一个 I2 遗留的契约违规**：`response.Meta.NextCursor` 原来带
> `omitempty`，导致最后一页（`next_cursor` 为 null）时这个 required 字段
> 被整个从 JSON 里去掉。冒烟测试跑在空目录上时精确踩中了这条路径——
> 这正是"每个迭代都要能演示"这条 DoD 的价值，单元测试用的都是非空数据，
> 从没触发过这个分支。

| 任务 | 内容 | 出处 | 依赖 | 判据 |
|---|---|---|---|---|
| **P1** | `ir/` 规范表示 + `protocol/openai`（chat，含流式） | 统一 §10 | S1 | OpenAI SDK 直连可用 |
| **B3** | `/v1/chat/completions`（含流式）、单渠道直连、请求日志 | 架构 §6.1 | P1 | SSE 正常；客户端断开能取消上游 |
| **B3a** | 两个流式超时（`firstByteTimeout` + `stallTimeout`） | 统一 §7 | B3 | 上游中途卡住能被 stall 超时终止 |
| **M2** | `request_logs` 三字段拆分 + `usage_source` + attempt 级记录 | 计价 §2、§4 | B3 | 成本与售价可分别查询；估算条目可筛 |

> **M2 必须在 B3 落地的同一个迭代。** 它只是三个字段的取舍，现在改零成本；
> 等有了一个月生产数据就是一次数据迁移加一次账单口径解释。

**风险前置验证点**：本迭代结束时必须能演示"上游中途断流 → 客户端收到明确的 error 事件，而不是一个假的 `finish_reason: stop`"（统一 §7）。做不到就不要进 I4。

> **2026-09-09 重估。** 对照 GPUStack 及其硬件抽象层 `gpustack-runtime` 的源码复核后

> **G1 从"起个 daemon 抓指标"变成了三块独立的工作**：设备检测层、指标归一化层、记账与对账。
> 原来的 4 周估算是把 G1 当成一个任务估的。这里把它拆开重估，**不是范围蔓延，
> 是原估算漏了**——漏掉的每一块在事后补的代价都远高于现在做。

| 任务 | 内容 | 出处 | 依赖 | 判据 |
|---|---|---|---|---|

| **G1a** | **设备检测层**：清单/用量查询分离、UUID 身份、拓扑距离矩阵、**带硬超时的健康检查** | 自建 §11.3 | G0 | **拔掉一张卡 / 模拟一张卡查询挂死，节点仍上报 READY 且其余卡正常** |
| **G1b** | **指标层**：DCGM + 引擎双层采集、**版本感知的指标名归一化**、Prometheus http_sd | 自建 §6.1、§6.2 | G1a、X3 | GPU 监控页接真实数据；**换一个 vLLM 大版本，看板不断线** |
| **G1c** | **GPU 记账与对账**：已分配量从绑定关系派生 + `allocated`/`used` 双指标告警 | 自建 §11.3、§6.3 | G1a | 三方对账无漂移；人工起一个占卡容器能被检出 |

| **G3** | Docker API 生命周期 + 调谐循环 + 缩容选实例打分 + **调度器 dry-run 端点** | 自建 §3.4、§11.2/11.4/11.5、§11.6 | G2 | drain 不中断在途请求；动作幂等；**杀掉 Control 后重启，不误杀任何健康实例**；缩容优先杀不健康副本 |
| **B7** | admin 的 infra 五页接真实数据 | 架构 §9 | G1a–G3 | 部署实例页可用；**容量评估页走后端 dry-run，不再用前端 `lib/capacity`** |

**三条本迭代必须做对、事后补代价极高的事：**

> **① G1 的对账不能省。** GPU 记账漂移会以"CUDA OOM"的面目出现，
> 排查方向完全是错的（自建 §9）。按新的建模（已分配量从绑定关系派生，
> 自建 §11.3），这一层的成本已降到"加两条 Prometheus 告警规则"。
>
> **② G0 的表形状一旦有生产数据就是迁移。** 与 `request_logs`（M2 ≤ I3）同一性质。
> 尤其是设备标识——现在只有一个 `index` 字段，会被"调度记账"和"拼 `/dev/` 路径"
> 两种用途混用，**混用的后果是给容器挂了另一张卡的设备节点**。
>
> **③ G7 的 TPOT 口径要在本迭代定死，虽然 G7 排在 I9+。**
> 「每 token 时间」有两个互相冲突的定义，短输出下差 40%（自建 §12.2）。
> G1b 的指标归一化表里就要把两者分开命名并入库；等 G7 才发现口径错了，
> 之前积累的全部历史数据都不可比。**这是一条跨迭代的决策依赖，不是实现依赖。**

**本迭代新增的两类"静默失败"风险**，在 G3 的验收里要专门演练（见 §6 风险登记）：
`--privileged` 击穿设备隔离、`CUDA_DEVICE_ORDER` 导致容器内外 GPU 编号错位。
两者都不报错，只产生错误的结果。

```
I0 ─┬─ S0 ─ S1 ──────────────────────────────────┐
    └─ B0 ─┬─ B1 ─────────────────────────┐      │
           ├─ X5(admin身份) ──────────────┤      │
           └─ B2 ─┬─ M1 ─ M1a ─ M1b ──────┤      │
                  │                        │      │
                  P1 ─ B3 ─ M2 ─┬─ P2 ─ P3 ┼─ B4 │
                                │          │      │
                                └─ M3 ─ M4 ─ M5 ─ B5
                                              │
                                              ├─ I6（管理端 34 端点）
                                              │
                    G0 ─ G1a ─┬─ G1b ─────────┼─ G4 ─ G5+M7
                              ├─ G1c          │
                              └─ G2 ─ G3 ─────┘
                                       └─ B7
```

**六条不能违反的顺序约束**（前四条原有，后两条本次新增）：

1. **M2 ≤ I3**：`request_logs` 有生产数据后再改就是迁移
2. **M1 ≤ B2 上线**：目录页展示的价格必须来自价目表，不能先用假数据（否则 M1b 的"同源"判据无从验证）
3. **G4 > P3**：自建接入路由依赖评分引擎存在
4. **X5 < I6**：34 个端点的鉴权主体必须先存在
5. **G0 ≤ G1a**（新增）：`nodes` / `gpus` 的表形状与 `request_logs` 同一性质——
   有生产数据后再改就是迁移。尤其是设备标识三字段（uuid / 枚举序 / device minor），
   **合成一个 `index` 字段会被两种用途混用，后果是给容器挂了另一张卡的设备节点**。
6. **G4 > G1b**（新增，加强了原来的"G4 > G3"）：自建的溢出信号取自引擎队列深度指标，
   指标层不到位则 G4 的评分拿不到输入。见 I8 的说明。

另有一条**跨迭代的决策依赖**（不是实现依赖，但同样不能违反）：

- **G7 的 TPOT 口径必须在 I7 定死。** G7 排在 I9+，但它依赖的指标口径在 G1b 就要落库。
  「每 token 时间」的两个定义在短输出下差 40%（自建 §12.2），等 G7 才发现选错，
  之前积累的历史数据全部不可比。**决定可以提前做，不必等到实现那一刻。**
