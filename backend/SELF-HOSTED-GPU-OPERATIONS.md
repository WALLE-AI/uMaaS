## 1. 三层供给，三种经济体

已确认**自有机房与云上 GPU 实例都有**，加上云端 API，供给实际分三层。把它们当同一类"渠道"处理是最容易犯的错——三者的成本结构几乎处处不同：

| | ① 自有机房 GPU | ② 云上 GPU 实例 | ③ 云端 API |
|---|---|---|---|
| 成本结构 | **纯固定**（已购/已折旧） | **按小时**，且常有最小计费单位 | **按 token** |
| 边际成本 | ≈ 0 | 实例已开：≈ 0<br>需新开：**一整小时起** | 每 token 都付钱 |
| 闲置代价 | **全额浪费**，关机也不省 | 可关机止损 | 无 |
| 容量上限 | **卡就这么多，硬顶** | 受配额与预算限制 | 近似无限 |
| 扩容时间 | 3–8 分钟（加载权重） | **10–20 分钟**（+ 开实例、无本地缓存） | 毫秒 |
| 缩容意义 | 只为腾卡给别的模型 | **真的省钱**，可 scale-to-zero | — |
| 过载表现 | 排队，TTFT 线性劣化 | 同左 | 429 拒绝 |

由此得到三条不同的运营目标：

- **自有机房：尽量用满。** 闲置是纯亏，且关机也不省钱。它应该是流量的第一去处
- **云上实例：按需开合。** 它的价值是"自有机房不够时的弹性缓冲"，但开销是阶跃的——不用时就该关掉
- **云端 API：兜底。** 只在前两层都吃不下时接手

**注意云上 GPU 的成本是阶跃而非连续的**。已启动的实例多跑一个请求不额外花钱，但从 0 到 1 要付一整个计费周期。这让"要不要为这波流量开一台"变成一个真实的决策，而不是自动伸缩就能解决的问题（§3.2）。

## 2. 混合供给的路由：不写死规则，把特征喂进评分

直觉做法是写一条规则：「优先自建，自建满了走云端」。**不要这么做**——它需要人工定义"满了"的阈值，而这个阈值随模型、并发、上下文长度变化；而且一旦自建实例劣化（比如某张卡降频），硬规则会固执地继续往上打。

正确做法是**复用 `UNIFIED-PROVIDER-INTERFACE.md` §5.5 已有的评分引擎**，只是把自建的真实特征喂进去，让"优先自建"和"饱和溢出"成为**涌现结果**而非硬编码：

```
effective = (w_rel·reliability + w_speed·speed + w_intel·intelligence)
            × headroomFactor × rateLimitFactor
            × costFactor            ← 新增维度
```

三处对接：

**① `costFactor` 让自建自然胜出。** 自建的边际成本≈0，成本因子取满分；云端按实际单价归一化。在任何成本敏感的策略下，自建自动排在前面——不需要任何"优先自建"的 if 语句。

**② 队列深度进 `speed` 因子，让饱和自动溢出。** 自建实例过载的表现不是 429 而是排队，TTFT 线性上升。把实例的**排队深度与近期 TTFT** 喂进 speed 维度后，随着队列变长，speed 分下降，effective 分随之下降，云端渠道自然反超——**溢出是连续的，不是阈值触发的开关**。

这一点很关键：阈值式溢出会在临界点附近抖动（一会儿走自建一会儿走云端），而连续评分不会。

> **［GPUStack 反例］这一条不是可选项。** GPUStack 的路由是"静态权重 + 按状态码
> fallback（4xx/5xx）"，配置在网关（Higress）上。这套在自建过载时**完全失灵**——
> vLLM 过载不返回 5xx，它只是把请求排进队列，TTFT 线性劣化直到超时。
> 状态码触发的 fallback 永远等不到那个状态码。
> **所以自建供给的溢出信号必须取自引擎的队列深度指标，而不是 HTTP 响应。**
> 相应地，§6 的 `num_requests_waiting` 不是"锦上添花的监控项"，而是**路由的输入**，
> 它的采集链路（引擎 → Agent → Prometheus → 评分引擎）要按关键路径对待，
> 采集中断时该实例的 speed 分应当降级而非按缺省值满分。

**③ `headroomFactor` 用显存水位而非配额。** 云端渠道的 headroom 是"剩余免费额度"，自建是"剩余 KV Cache 空间"。同一个 ramp 函数，喂不同的量。显存逼近上限时实例即将拒绝新请求，提前压低分数比等它报错更好。

**`costFactor` 要分三档，不是两档**（对应 §1 的三层供给）：

| 供给 | costFactor | 说明 |
|---|---|---|
| 自有机房 | 满分 | 边际成本≈0 且闲置纯亏，最该优先 |
| 云上实例（已启动） | 接近满分 | 已经在计费了，多跑一个请求不额外花钱 |
| 云上实例（需新开） | **不参与本次评分** | 冷启动 10–20 分钟，救不了当前请求。是容量决策而非路由决策（§3.2） |
| 云端 API | 按单价归一化 | 每 token 都花钱 |

第三行是个容易搞混的地方：**"要不要开一台云上 GPU"不是路由问题**。当前这个请求等不了 10 分钟，只能在已有容量里选。开机与否是容量层的异步决策。

### 2.1 数据驻留是硬约束，不是打分项

同时拥有自有机房，往往意味着**有些数据不能出内网**。这类要求不能用评分表达——分数再低也仍有被选中的可能，而合规要求是零容忍的。

因此在评分之前先做**可行集过滤**：

```
候选集 = 支持该模型的供给
       ∩ 满足数据驻留要求的供给     ← 硬过滤，不参与打分
       ∩ 健康 ∩ 分组可见 ∩ 能力满足
```

数据驻留标记需要落到三处：

- **工作空间级**：`workspaces.data_residency`（`any` / `on_premise_only`），企业客户可要求
- **模型级**：私有微调模型天然只在自有机房
- **请求级**：请求头可声明更严格的要求，但不能放宽工作空间的设置

**若过滤后候选集为空，必须明确报错**，而不是"降级"到云端——这正是数据驻留要防的事。错误信息要说清是驻留约束导致的，否则运维会往容量方向排查。

同理，某些模型只在自建有（私有微调），某些只在云端有，这也是可行集约束而非打分项。

## 3. 容量管理：时间常数决定了必须预测而非响应

云端渠道的容量调整是毫秒级的——切个渠道就行。自建不是：

```
新增一个 Qwen3-72B 实例的时间构成
├── 调度到有空闲 GPU 的节点        秒级
├── 拉取镜像（若无缓存）           1–3 分钟
├── 从共享存储加载 145GB 权重      2–5 分钟   ← 主要成本
├── CUDA graph 捕获与预热          30–60 秒
└── 健康检查通过、纳入路由         10 秒
                                   ─────────
                                   合计 3–8 分钟
```

云上 GPU 实例更慢——还要加上开实例、拉镜像（无本地缓存）、从对象存储下载 145GB 权重：**10–20 分钟**。

**这条时间线里有两段是可以靠配置压掉的**［GPUStack 验证］：

- **CUDA graph 捕获与 torch.compile 编译产物要持久化。** vLLM 用
  `VLLM_CACHE_ROOT` 指定编译缓存目录，默认落在容器内，容器一销毁就没了，
  **每次重启都重新编译一遍**。把它挂到节点上的持久目录，同一模型的
  第二次启动可以省掉 30–90 秒。这一项几乎零成本，但只有知道有这个变量才会做。
- **`OMP_NUM_THREADS=1`。** 默认 OpenMP 会按核数起线程，在权重加载阶段
  与 IO 抢 CPU，反而拖慢加载。

反过来，有一项会**拖长**冷启动而且容易被忽略：默认按模型声明的最大上下文
（可能是 128k）分配 KV Cache，会让显存需求和预热时间都膨胀。GPUStack 的做法是
**在用户未显式指定时，把 `--max-model-len` 自动压到 8192**。我们的部署配置里
`max_model_len` 应当有一个显式的平台默认值，而不是"跟随模型"。

**结论：自建容量必须预测性扩容，不能等过载了再加。** 等 TTFT 已经劣化再扩，用户已经难受了 5–20 分钟。

四层应对，按时间尺度递进：

| 层次 | 时间尺度 | 手段 | 成本性质 |
|---|---|---|---|
| **瞬时** | 秒 | 溢出到云端 API（§2 的连续评分自动完成） | 按 token，贵但立即可用 |
| **短期** | 分钟 | 自有机房内起新实例（有空闲卡时） | 只有加载时间成本 |
| **中期** | 10–20 分钟 | 开云上 GPU 实例 | 按小时，阶跃计费 |
| **长期** | 小时/天 | 按历史流量曲线预排程 | 提前量换成本 |

### 3.1 先用满自有机房，这不需要算账

自有机房的卡**关机也不省钱**，所以只要有空闲卡且有排队请求，起实例永远是对的。这一层没有权衡，唯一的约束是加载时间。

**唯一要算的是"起哪个模型"**——空闲卡有限时，优先给排队最严重、或单位 token 价值最高的模型。

### 3.2 云上实例的开合是真实的成本决策

这一层要算账，因为开一台就要付一整个计费周期：

```
开云上实例划算的条件：
  预计溢出到 API 的 token 量 × API 单价
      >  实例小时成本 × 预计运行小时数 + 冷启动期间仍需溢出的成本
```

三个实践约束：

- **最小存活时间**。既然按小时计费，开了就至少跑满一个周期，别 10 分钟后又关掉——那等于白付
- **冷启动期间仍要溢出**。10–20 分钟里流量不会等，这部分成本要算进上式
- **scale-to-zero 是云上实例独有的价值**。夜间流量低谷时全部关掉，自有机房兜底即可。自有机房没有这个选项

### 3.3 预热池只对自有机房有意义

一个待命的自有机房实例，**成本已经沉没**——机器在那里，跑不跑都一样。所以预热池在自有机房是"免费"的，只占用卡。

而云上的预热实例每小时都在烧钱，除非能证明溢出成本更高，否则不该常备。

**缩容比扩容更需要小心**：正在处理请求的实例不能直接杀。必须先从路由摘除（停止接新请求），等在途请求自然结束或超时，再回收。drain 超时取 `max_output_tokens ÷ 最慢生成速度`，通常 2–5 分钟（与 §11.4 的状态机一致）。

### 3.4 缩容要先回答"杀哪一个"

「怎么安全地杀」只是问题的后一半，前一半是「杀哪个副本」——这一点很容易漏掉，
然后实现成"杀列表里的第一个"，结果把唯一健康的副本杀了，留下两个 ERROR 的。

［GPUStack 验证］正确做法是**给现存实例打分，杀最低分的**，打分链与扩容时相反：

| 打分维度 | 相对权重 | 含义 |
|---|---:|---|
| **健康状态** | 100 | 节点 NOT_READY 或实例 ERROR → 0 分，优先杀 |
| **放置** | 1 | 与扩容同一个 binpack/spread 策略，但解读为"保留偏好" |

权重差两个数量级是有意的：**健康度压倒一切**，放置只在健康度打平时起作用。

还有一条并发正确性要求：查询待缩容实例时要**加行锁**（`SELECT ... FOR UPDATE`），
否则会和调度器争抢同一批实例——调度器刚给某个 PENDING 实例分配了节点，
缩容逻辑同时把它算进"现存副本数"里删掉。

### 3.5 长期预排程：cron 窗口，不是指标反馈

§3 的四层里"长期"那一层落地成什么？［GPUStack 验证］的形态是
**cron 定时窗口**，语义对齐 KEDA Cron scaler：

```
规则 = (start_cron, duration_seconds, replicas)
窗口在 start_cron 触发时打开，持续 duration_seconds
窗口重叠：最近开启的赢；同时开启取 replicas 较大者（结果与规则顺序无关）
所有窗口之外：回落 baseline_replicas
```

三条实现要点：

- **定时器只写"期望副本数"，不直接创建实例**。实际扩缩交给 §11.5 的调谐循环。
  职责一分开，定时器就变成一个纯函数，可以单测。
- **cron 在平台统一业务时区求值**，不做每模型时区。与用量 rollup 共用同一个时区解析。
- **窗口结束时间要用绝对时间相加**（先转 UTC 再加 duration），不能墙钟相加，
  否则跨夏令时的窗口会莫名多一小时或少一小时。

**为什么不是指标驱动的自动伸缩？** 因为扩容时间常数是 3–8 分钟（§3 开头），
在这个量级上做反馈环极易震荡。我们比 GPUStack 多一条兜底路径（溢出到云端 API），
所以可以做**预测性**扩容（按历史曲线提前拉起），但不建议做
"队列一长就扩、一短就缩"的闭环——那会在每个流量波峰上反复起停实例。

## 4. 自建模型的成本核算：摊销值，不是定价

`frontend/admin` 的模型分析页显示 `$/1M tokens`，用于云端与自建对比。**自建的这个数字有本质不同，必须标注清楚，否则会误导决策。**

```
自建单位成本 = (GPU 小时成本 × 实例运行小时数 + 存储与网络分摊)
              ÷ 该时段实际产出的 token 数
```

关键性质：**它是利用率的函数，不是常数。**

| GPU 利用率 | H100 月成本 | 月产出 tokens | 单位成本 |
|---|---|---|---|
| 20% | $2,000 | 0.9B | **$2.22 / 1M** |
| 50% | $2,000 | 2.2B | $0.91 / 1M |
| 80% | $2,000 | 3.5B | **$0.57 / 1M** |

（数量级示意，实际取决于模型与序列长度）

**利用率 20% 时，自建可能比云端 API 还贵。** 这是"自建一定更便宜"这个直觉最常翻车的地方。

因此在 admin 的分析页上，自建模型的成本必须：

1. **标注为「摊销成本」**，与云端的「供应商计价」区分显示
2. **附带当期利用率**，让读者知道这个数字的前提
3. **给出盈亏平衡利用率**——低于这条线，自建不如直接买 API

自建请求的成本字段填的是**摊销值**，需要一个后台任务按周期回填（请求发生时还不知道当期最终利用率）。这意味着自建请求的成本数字**在当期结束前是估算值**，UI 上要能区分。

### 4.1 机时计量必须幂等，靠行上的水位线

回填任务是**周期性重跑**的：进程重启、tick 重叠、事件重放、同一小时内实例
stop→start，都会让同一段时间被处理不止一次。没有幂等机制，GPU 机时会被重复累加，
而这种错误**没有任何症状**——数字只是偏大，不会报错。

［GPUStack 验证］的做法是**把游标落在数据行上，不只在内存里**：

```
gpu_usage_rollup 表：
  (deployment_id, hour_bucket, sku, sku_count)  ← 唯一键
  quantity        累计秒数
  settled_until   ★ 该行已结算到的时刻（持久化水位线）

结算逻辑：只累加 [settled_until, window_end) 这一段，然后前推 settled_until
```

重跑同一个窗口时，`[settled_until, window_end)` 是空区间，加 0。**天然幂等，
不需要分布式锁，也不怕进程在任意时刻被杀。**

三条配套约束：

- **按 UTC 整点切片。** 一个跨小时的运行窗口要拆成多行，否则按小时/按天的
  聚合查询都得做区间相交，代价高且容易算错。
- **机型标识存快照，不存外键。** 机型可以下线，但下线时还在跑的实例要按原机型计价。
  查机型行时**忽略软删标记**——这正是那张表要软删而不是硬删的原因。
- **算不出计费份额的窗口就不结算，留到下个 tick 重试。**
  ［GPUStack 验证］的注释写得很直白："fallback to a whole card would silently
  overcharge"。**宁可延迟出账，不可默认多收。**

> ⚠️ **回填的目标字段以 [计价与计费方案 §4.4](./BILLING-AND-PRICING.md) 为准。**
> `ARCHITECTURE.md` §4.3 原本的 `cost_usd_micro` 一个字段同时承担成本与售价，
> 若回填写在它上面，**用户已经付过的账单会在月末被静默改掉**。该文已把它拆为
> `upstream_cost_nano`（可回填）与 `charged_amount_nano`（不可变），
> 并要求回填路径在代码层禁止触碰后者。本节的回填任务只写前者。

## 5. 权重存储与分发

145GB 一个模型，多节点部署同一模型时如何分发，是自建绕不开的工程问题。

| 方案 | 首次加载 | 后续加载 | 运维 |
|---|---|---|---|
| **共享存储（NFS/CephFS）** | 慢（网络带宽瓶颈） | 慢，每次都走网络 | 简单 |
| **对象存储 + 节点本地缓存** ✅ | 慢（一次） | **快（本地 SSD）** | 中等，要管缓存淘汰 |
| 每节点独立下载 | 慢 | 快 | 浪费带宽与磁盘 |

推荐**对象存储（S3/OSS）为权威副本 + 节点本地 SSD 缓存**：

- 权重不可变（同一 revision 内容固定），缓存不需要失效逻辑，只需要 LRU 淘汰
- 节点本地缓存命中时，加载时间从"网络传 145GB"降到"本地 SSD 读 145GB"，差一个数量级
- 缓存淘汰按「最近未使用 + 当前无实例引用」，正在被实例使用的权重不能淘汰

**磁盘容量是硬约束**：一个节点缓存 4–5 个大模型就要 1TB 级别。`frontend/admin` 的模型仓库页已有磁盘水位显示，后端要提供每节点的缓存占用与命中率。

### 5.1 权重副本要建模成一等资源

［GPUStack 验证］「某个模型在某个节点上有没有」不应该靠"扫一遍磁盘"回答，
而应该是一张表：

```
model_file_replicas  id, node_id, model_id, source_index,
                     state(downloading|ready|error), progress,
                     resolved_paths, size_bytes, sha256_verified,
                     last_used_at, ref_count
```

有了这张表，四件事同时被解决：

1. **调度时的本地性判断**是一次索引查询，不是 N 次远程探测（§11.2）。
2. **实例只有在 `state=ready` 后才能进入启动阶段**——这条边由调谐循环强制，
   避免容器起来后卡在"找不到权重"。
3. **LRU 淘汰有依据**：`last_used_at` + `ref_count > 0` 的不能动。
4. **磁盘水位与命中率**直接从表里聚合，不用 Agent 额外上报。

两个实现细节，不做会慢慢出问题：

- **下载放独立进程/协程池，有并发上限**（GPUStack 取
  `min(配置值, CPU 核数)`），且必须**可取消**——用户删掉一个正在下载的
  145GB 模型，任务要能立刻停，而不是把盘写满再说。
- **失败与取消要清理残留**。HuggingFace 的断点文件是
  `<name>.<etag>.incomplete` 加同名 `.lock` / `.metadata`，
  文件名里编码了 etag，得反查才能定位。不清理的话磁盘会被慢慢吃光，
  而且表里显示"未下载"、盘上却占着空间。

## 6. 可观测：两层指标，缺一不可

`ARCHITECTURE.md` §4.4 已定「GPU 实时指标不入库，从 Prometheus 查」。这里补充**必须同时采集两层**：

**第一层：硬件（DCGM Exporter）**

利用率、显存、温度、功耗、SM 时钟、ECC 单/双位错误、XID、NVLink 带宽、降频原因。

**第二层：推理引擎（vLLM / SGLang 自身的 `/metrics`）**

这一层比硬件层更贴近用户体验，却经常被忽略：

| 归一化指标名 | 为什么必须有 |
|---|---|
| `umaas:num_requests_running` / `umaas:num_requests_waiting` | **队列深度**，§2 的溢出判断直接依赖它 |
| `umaas:kv_cache_usage_ratio` | KV Cache 水位，比显存总量更能预测"还能接多少并发" |
| `umaas:time_to_first_token_seconds` | 引擎侧 TTFT，与网关侧对比可分离出网络耗时 |
| `umaas:inter_token_latency_seconds` | 纯解码期的 token 间隔（**注意与下一项的区别，见 §12.2**） |
| `umaas:time_per_output_token_seconds` | 端到端每 token 时间（含 TTFT 摊销） |
| `umaas:request_preemptions` | **抢占次数**。KV Cache 不足时 vLLM 会抢占已有序列，这是过载的明确信号 |
| `umaas:prefix_cache_hits` / `queries` | 前缀缓存命中率，直接影响单位成本（§4） |

**只看 GPU 利用率会误判**：利用率 95% 可能是健康的满负荷，也可能是在反复抢占重算。`num_preemptions` 才能区分这两种情况。

### 6.1 引擎指标名必须做版本感知的归一化

**这是一个会静默失效的坑，必须在 G1 就做对。**［GPUStack 验证］

vLLM 至少改过两次核心指标名：

| 旧名 | 新名 | 变更版本 |
|---|---|---|
| `vllm:gpu_cache_usage_perc` | `vllm:kv_cache_usage_perc` | 0.9.2 |
| `vllm:time_per_output_token_seconds` | `vllm:request_time_per_output_token_seconds` | 0.11.0 |
| `vllm:num_requests_swapped` | （移除） | 0.11.1 |

任何把 vLLM 原始指标名写死进告警规则、看板或**路由评分逻辑**的系统，
都会在升级引擎的那天失效——而且**看板上显示为一条平线，不是报错**。
更糟的是 §2 的溢出判断会因为读不到队列深度而按缺省值给满分，
把流量继续往一个已经过载的实例上打。

所以指标层要有一张**带版本区间的映射表**，而不是一组常量：

```yaml
runtime_mapping:
  vLLM:
    "*":                                    # 当前版本
      vllm:num_requests_waiting:            umaas:num_requests_waiting
      vllm:kv_cache_usage_perc:             umaas:kv_cache_usage_ratio
      vllm:num_preemptions:                 umaas:request_preemptions
      vllm:request_time_per_output_token_seconds: umaas:time_per_output_token_seconds
    "<0.11.0":
      vllm:time_per_output_token_seconds:   umaas:time_per_output_token_seconds
    "<0.9.2":
      vllm:gpu_cache_usage_perc:            umaas:kv_cache_usage_ratio
```

配套三条：

- **版本要向实例问，不要信配置。** 启动时打一次引擎的版本端点，
  把结果写回 `deployments.detected_engine_version`。配置里写的版本
  可能是"auto"，也可能被镜像 tag 骗到。
- **同时暴露归一化与原始两个端点**：`/metrics`（归一化，供告警与路由）
  与 `/metrics/raw`（原样透传 + 补上我们的标签，供深度排障）。
  归一化会丢信息，排障时需要原始形态。
- **映射表要能热更新**（放配置文件或 `settings` 表），
  否则每次引擎升级都要发一次二进制。

### 6.2 Prometheus 靠 http_sd 发现节点，不写静态列表

裸机集群的节点是动态的（加机器、下线、维护），
静态 `targets` 列表既不可维护也必然过期。

［GPUStack 验证］**让 Control 自己当服务发现源**——它本来就有权威的节点表：

```yaml
scrape_configs:
- job_name: umaas-node-discovery
  http_sd_configs:
  - url: 'http://control:9090/internal/metrics/targets'
    refresh_interval: 1m
```

`/internal/metrics/targets` 只返回**状态为 READY 且指标端口有效**的节点，
并打上 `cluster`、`region`、`node_id` 标签。机房节点若走隧道模式（§10.5），
要返回 Control 侧代理地址而不是节点内网地址——因此这个端点需要两个变体，
或用一个查询参数区分。

这一条几乎零成本，但省掉的是"每次加机器都要改 Prometheus 配置并 reload"。

### 6.3 对账信号是两条指标的差，不是一个额外的任务

§11.3 要求周期性三方对账。**其中"数据库记录 vs 实际占用"这一路
不需要单独写一个对账任务**——把两个量都做成指标即可：

| 指标 | 来源 |
|---|---|
| `umaas_gpu_vram_allocated_bytes` | 从 `deployments` 的绑定关系派生（§11.3） |
| `umaas_gpu_vram_used_bytes` | DCGM / `nvidia-smi` 实测 |

然后：

```
used > allocated + 阈值   → 有进程在账外用卡（人工起的容器、残留进程）
allocated > used + 阈值   → 账上有幽灵（记录没清、容器已退出）
```

做成两条告警规则就够了。**关键是两个量必须用同一套口径计算**——
GPUStack 的 Agent 侧导出 `gram_allocated` 时，特意调用了和服务端
完全相同的那个派生函数，就是为了保证两边算法一致，避免"对账工具自己算错"。

## 7. 与统一接口方案的衔接

自建模型走 `UNIFIED-PROVIDER-INTERFACE.md` §4.4 的 `openai_compatible` 驱动（vLLM/SGLang 都提供 OpenAI 兼容接口），**零协议适配代码**。但有三处差异要在 `ProviderProfile` 里表达：

```go
Quirks{
    // vLLM 的 max_model_len 在启动时固定，超过会直接报错而非截断
    MaxModelLenFixed: true,
    // 自建实例通常不做认证，或用简单的 bearer
    AuthScheme: AuthSchemeNone,
    // 支持 vLLM 特有的采样参数（top_k、repetition_penalty 等）
    ExtraSamplingParams: []string{"top_k", "repetition_penalty", "min_p"},
}
```

**模型名映射要注意**：vLLM 启动时用 `--served-model-name` 指定对外名字，若不指定则用权重路径。`channel_models.upstream_model_name` 必须与之一致，这是自建部署最常见的低级错误之一——部署成功、健康检查通过，但一调用就 404 model not found。

**正确的解法不是"预检清单里加一项"，而是从源头消灭这个不一致**［GPUStack 验证］：

- **`--served-model-name` 由平台强制注入**，取值恒等于
  `channel_models.upstream_model_name`，用户的 `backend_parameters` 里
  写了也以平台的为准（或直接拒绝该参数）。两个值来自同一个字段就不可能不一致。
- 在此之上再保留一层运行时验证：纳入路由前**用真实模型名发一个 1-token 请求**
  （§11.4 的第三层健康检查），挡住其他原因导致的 404。

### 7.1 引擎镜像版本必须是部署配置的一等字段

§11.4 示例里的 `vllm/vllm-openai:v0.9.0` 是写死的一行。真实运营中一定会出现：

- 新模型架构需要新版 vLLM；
- 老模型在新版 vLLM 上跑不起来（参数改名、算子行为变化）；
- 同一版 vLLM 有针对不同 CUDA 版本编译的多个镜像。

［GPUStack 验证］所以镜像解析要有明确的优先级链，而不是一个常量：

```
1. deployments.image_name          ← 用户显式指定，最高优先级
2. 按 engine + engine_version 查镜像目录表
3. 按 (GPU 厂商, 架构, 引擎, 引擎版本, 平台架构) 自动解析
   多个 CUDA 版本候选时：取 ≤ 宿主驱动的最新版；否则同大版本取最旧
```

以及一个容易踩的兼容性问题：**镜像的 CUDA 小版本高于宿主驱动**（同大版本）时，
容器工具链的 `NVIDIA_REQUIRE_CUDA` 检查会拒绝启动。可以注入
`NVIDIA_DISABLE_REQUIRE=1` 绕过（依赖驱动的次版本兼容性），但**默认应当关闭**——
它在部分消费级卡上会导致容器直接崩溃。做成按部署可开的开关，不要做成全局默认。

## 8. Infra Agent 的职责边界

| 职责 | 说明 |
|---|---|
| GPU 指标采集 | 抓 DCGM + 引擎 metrics，暴露给 Prometheus |
| 实例生命周期 | 创建、健康检查、drain、销毁；上报状态给 Control |
| 权重管理 | 从对象存储拉取到本地缓存、校验、LRU 淘汰 |
| 容量决策执行 | **执行**扩缩容指令，不做决策 |
| GPU 设备记账 | 维护本节点 GPU 占用状态并与实际对账（§11.3） |
| 压测执行 | 跑并发爬坡，回传结果 |

**明确不属于 Infra Agent 的**：

- **扩缩容决策**（属于 Control，因为决策要看全局流量与成本，Agent 只看本集群）
- **路由**（属于 Gateway）
- **计费**（属于 Control）

这条边界的意义：Agent 可以是"哑"的执行器，逻辑集中在 Control。多集群时 Agent 可以有多个实例，而决策仍然唯一。

［GPUStack 验证］这条边界在它的代码里被贯彻得非常彻底，有两个可以直接照搬的判据：

- **Agent 不上报"我用了哪几张卡"。** 它只上报硬件事实（有几张卡、各多大、
  当前温度功耗与实测占用）与容器实况。"哪张卡分配给了谁"是 Control 从
  绑定关系派生的（§11.3）。
- **Agent 收到的是具体的 `gpu_indices` 列表，不是"给我 4 张卡"。**
  它唯一的自主权是"拒绝执行"（比如发现这几张卡型号不一致时报错），
  没有"改选另外几张"的余地。

判断一个功能该不该放进 Agent，用一个问题就够：
**它需要看到本节点之外的信息吗？** 需要，就属于 Control。

## 9. 实施顺序

对应 `ARCHITECTURE.md` §9 的 B7，可细分为：

| 步骤 | 内容 | 判据 |
|---|---|---|
| **G1** | 每节点 Agent daemon + **GPU 检测（清单/用量分离、UUID 身份、带超时的健康检查）** + GPU/引擎双层指标（**含版本感知归一化 §6.1**）+ http_sd 发现（§6.2）+ **GPU 记账与对账**（§11.3、§6.3） | GPU 监控页接真实数据；三方对账无漂移；引擎升级后指标不断；**拔掉一张卡/模拟一张卡查询超时，节点仍上报 READY 且其余卡正常** |
| **G2** | 权重拉取 + `model_file_replicas` 表 + 节点本地缓存 + SHA256 校验 | 模型仓库页可用；缓存命中率可见；取消下载能立刻停 |
| **G3** | Docker API 生命周期 + 调谐循环（§11.4/11.5）+ 调度器 dry-run 端点（§11.6） | 部署实例页与容量评估页可用；drain 不中断在途请求；动作幂等；**杀掉 Control 后重启，不误杀任何健康实例** |
| **G4** | 自建接入路由（`costFactor` + 队列深度进评分） | **自建优先且饱和自动溢出，无硬编码规则** |
| **G5** | 成本核算与摊销回填（**含 `settled_until` 幂等 §4.1**） | 分析页显示摊销成本 + 当期利用率 + 盈亏平衡点；**回填任务连跑三次结果不变** |
| **G6** | 预热池与预测性扩缩容 + cron 预排程（§3.5） | 流量高峰前自动扩容，无人工介入 |
| **G7** | 压测执行（§12） | 压测页接真实数据；**结论区分拐点与扫描上限**；结果回写容量基准 |

**G1 的对账不能省。** GPU 记账漂移会以"CUDA OOM"的面目出现，排查方向完全是错的，代价远高于一开始就做对账。而按 §11.3 的建模（已分配量从绑定关系派生），这一层的成本已经降到"加两条 Prometheus 告警规则"。

**G3 的判据里那条压力测试是硬要求**：控制面重启、watch 断连、网络分区这三个场景要各演练一次，确认没有健康实例被回收。这是自研调谐循环唯一会造成用户可见故障的失败模式（§11.5.2）。

**G4 是价值拐点**：在此之前自建集群只是"被管理的资源"，之后才真正成为供给。建议 G1–G3 之后先做 G4，把 G5–G7 排在后面。

**但 §12.2 的 TPOT 定义必须在 G1 就定下来**，虽然 G7 才实现压测。因为 G1 的引擎指标归一化表里就要区分这两个指标，事后再改会让已积累的历史数据口径不一致。

## 10.5 混合基础设施的网络拓扑

自有机房 + 云上并存带来一个前面几节都没覆盖的问题：**后端服务在云上，而一部分 GPU 在机房，每个推理 token 都要跨网络。**

```
          客户端
             │
        ┌────▼─────────────────────────────┐
        │  云上 VPC                         │
        │  Control · Gateway · PG · Redis   │
        │            │        └─── 云上 GPU 实例（同 VPC，RTT <1ms）
        └────────────┼──────────────────────┘
                     │  ← 跨网络：VPN / 专线 / 公网+mTLS
        ┌────────────▼──────────────────────┐
        │  自有机房                          │
        │  Agent@node-01…N · vLLM 实例       │
        └───────────────────────────────────┘
```

### 跨网络对流式推理的实际影响

好消息是**没有想象中严重**：SSE 是持续的流式管道，不是每个 token 一次往返。延迟影响是一次性的，不随 token 数累加。

| 影响 | 量级 | 判断 |
|---|---|---|
| TTFT 增加 | 一个 RTT | 同城专线 2–5ms、跨城 20–50ms：**相对 400ms 基线可接受** |
| token 间隔 | 受抖动影响 | 抖动大时用户会看到"卡顿式"输出，体验劣于稳定但稍慢 |
| 出网带宽费 | 按 GB 计 | 文本 token 量小，通常可忽略；**多模态（图像/音频）要重新算** |
| 跨国 | RTT 200ms+ | **不可接受**，必须就近部署 |

### 三种拓扑选择

| 方案 | 适用 | 代价 |
|---|---|---|
| **单 Gateway 在云上** ✅ 首版 | 同城/同区域，RTT < 50ms | 机房 GPU 的响应多一个 RTT |
| **机房也部署 Gateway，就近路由** | 跨区域或对 TTFT 敏感 | 多一套部署；需要在入口做地理路由 |
| 专线打通，视为同一网络 | 预算充足 | 成本高，但拓扑最简单 |

**首版建议单 Gateway 在云上**，前提是机房与云上同城或同区域。这保持了 `SERVICE-DECOMPOSITION.md` 的拓扑不变，不引入多 Gateway 的一致性问题（缓存失效要广播到所有 Gateway 实例）。

若将来 TTFT 成为瓶颈，再按"机房部署第二个 Gateway + 就近路由"演进——`SERVICE-DECOMPOSITION.md` §4 的装配层已经支持多实例部署，这不是重构。

### 10.5.1 同城单 Gateway 的网络实施要点

拓扑已定为单 Gateway，机房与云上同城。这条链路承载两类流量，带宽需求相差三个数量级：

| 流量 | 带宽需求 | 时延敏感 |
|---|---|---|
| 推理 token 流（Gateway ↔ vLLM） | **小**（文本，几十 KB/请求） | **高**，直接进 TTFT |
| 权重同步（对象存储 → 机房 MinIO） | **极大**（单模型 145GB） | 低，可限速、可夜间 |

**必须给这两类流量分开的通道或限速策略**。否则一次模型同步会把链路占满，导致所有在途推理请求的 token 间隔飙升——用户看到的是"突然变卡"，而排查方向很容易跑偏到 GPU 上。最简做法是给权重同步任务设带宽上限（如链路的 30%），并优先安排在低谷时段。

链路方式的取舍：

| 方式 | 时延 | 适用 |
|---|---|---|
| **云厂商专线** ✅ | 1–3ms，稳定 | 推荐。同城专线成本可控，抖动小 |
| IPSec / WireGuard VPN | 3–10ms，受公网抖动影响 | 起步阶段可用，注意加密开销与 MTU |
| 公网 + mTLS | 不可控 | 仅限验证环境 |

**抖动比平均延迟更值得关注**。流式输出下，平均 5ms 但偶发 200ms 的链路，体验差于稳定 20ms 的链路——前者会让 token 输出呈现可见的顿挫。监控要看 p99 而非均值。

**单链路是单点。** 专线中断时机房 GPU 全部不可达，此时应当自动溢出到云上实例与云端 API（§2 的评分会因健康检查失败自动完成，无需额外逻辑）。但要确认：**云端 API 的配额足以承接机房的全部流量**，否则链路故障会直接变成服务不可用。这个容量假设要定期用演练验证。

### Agent 的连接方向：一律由 Agent 主动外联

**机房 Agent 主动连 Control，而不是 Control 去连 Agent。** 三个理由：

1. 机房通常在 NAT 后，没有公网入站地址
2. 不需要在机房防火墙上开入站端口——这是安全审计最容易卡住的地方
3. 连接方向统一后，云上 Agent 与机房 Agent 的代码完全一致，不必分支处理

具体做法：Agent 启动后建立到 Control 的 **gRPC 长连接（双向流）**，指令经由这条连接下发，状态经由它上报。连接断开时 Agent 按指数退避重连（1s → 60s，带 30% 抖动），**期间已运行的实例不受影响**（这一点很重要——控制面故障不该影响数据面）。

**但控制通道解决不了数据通道。** 推理请求要从云上 Gateway 打到机房的 vLLM 实例，
这条路径也需要能穿透 NAT。［GPUStack 验证］如果专线/VPN 不可用（或作为其降级路径），
可以复用同一条外联连接做隧道：

```
Agent 外联时携带自己可达的网段（如 10.0.1.23/32）
Control 侧用前缀树登记，并为该 Agent 分配一个本地代理地址
Gateway 的上游注册项指向这个「Control 侧代理地址」，而不是机房内网地址
请求到达 → 代理经隧道下发连接请求 → Agent 侧主动连本地实例 → 双向流转发
```

关键的一条：**上游地址在隧道连上之前是不存在的。**
所以"隧道断开"要自然表达为"这个上游从 Gateway 配置里消失"，
而不是"上游还在但连不上"——前者会让流量按 §2 的评分自动流向别处，
后者会持续产生失败请求。实现上就是：生成上游注册项的函数在
`proxy_address == nil` 时返回空，而不是返回一个占位地址。

节点 IP 变化时，最简单的处理是**主动断开重连**让 Control 重新登记，
不要设计一个"更新网段"的消息类型——重连路径本来就必须正确，复用它即可。

### 权重存储要分区域

§5 定的"对象存储 + 节点本地缓存"在混合形态下要注意：机房节点从云上对象存储拉 145GB 会很慢且产生流量费。

- **机房侧部署本地对象存储或镜像缓存**（MinIO 即可），权重先同步一次，之后机房节点从本地拉
- 云上节点直接用云厂商对象存储
- 两边的权重版本由 Control 统一记账，`local_models` 表加 `region` 维度

## 11. 裸机 + Docker 的实现方案

编排底座已定为裸机 + Docker。这一节回答"具体怎么做"，并诚实说明放弃 K8s 的代价落在哪里。

### 11.1 先看清楚 K8s 免费给了什么

选裸机意味着以下能力要么自己实现，要么放弃：

| K8s 提供 | 裸机方案 | 工作量 |
|---|---|---|
| 跨节点调度 | **自己实现**（§11.2） | 中，节点少时可控 |
| GPU 设备插件与分配记账 | **自己实现**（§11.3） | 中，且**是最容易出事的一处** |
| 声明式期望状态 + 调谐循环 | **自己实现**（§11.4） | 中 |
| 健康检查与自动重启 | Docker `restart` + Agent 探针 | 小 |
| 滚动更新 | 自己实现（先起新后停旧） | 小 |
| 服务发现 | 不需要（实例地址由 Control 记录并下发） | — |
| 资源隔离 | Docker `--cpus` / `--memory` / `--gpus` | 小 |

**这不是一个"K8s 更好"的论证**——节点数在 5–10 台、模型部署不频繁的前提下，自研这几块的复杂度远低于维护一套 K8s + GPU Operator。但要认清工作量落在调度与设备记账上，这两块必须做扎实。

### 11.2 docker-compose 是单机工具，跨节点必须自己编排

**这是选定裸机后第一个要解决的问题。** compose 无法跨节点。因此明确区分两类部署：

| 部署对象 | 拓扑 | 手段 |
|---|---|---|
| **平台服务**（Control / Gateway / Postgres / Redis / Prometheus） | 固定 | **docker-compose**，人工或 CI 管理 |
| **推理实例**（vLLM 容器） | 动态，随扩缩容变化 | **Docker Engine API**，由 Agent 程序化创建 |

推理实例**不要**用"生成 compose 文件再 shell out 执行"的方式。用 Go SDK（`github.com/docker/docker/client`）直连本机 `/var/run/docker.sock`：

- 能拿到容器 ID、精确状态、日志流（部署页的实时日志直接来自这里）
- 错误可结构化处理，不必解析 CLI 输出
- 无临时文件生命周期问题

**Agent 是每节点一个的 daemon，不是集中式单实例。**

```
        ┌──────────────── Control（云上） ────────────────┐
        │  全局调度决策 · 实例期望状态 · 成本与容量核算    │
        └───────┬──────────────┬──────────────┬───────────┘
                │ gRPC         │              │
        ┌───────▼──────┐ ┌─────▼────────┐ ┌───▼──────────┐
        │ Agent@node-01│ │ Agent@node-02│ │ Agent@node-0N│
        │ docker.sock  │ │ docker.sock  │ │ docker.sock  │
        │ DCGM · 权重  │ │              │ │              │
        └──────────────┘ └──────────────┘ └──────────────┘
```

**每个 Agent 只碰本机的 docker socket**，不暴露 Docker TCP 端口。这一条是安全底线——Docker API 未加固时等同于宿主机 root，绝不能开在网络上。Agent 与 Control 之间用 mTLS 的 gRPC。

调度策略在当前规模用最简的即可，不必上装箱算法。但**结构必须分成"过滤"与"打分"
两段**，两者不可混用［GPUStack 验证］：

```
① 过滤（硬约束，不满足就出局）
   节点状态 READY
   ∩ 标签选择器匹配
   ∩ 引擎/驱动版本兼容
   ∩ 满足数据驻留要求（§2.1）
   ∩ 有足够的、互联距离足够近的空闲 GPU，且显存比例满足 gmu（§11.3）
   ∩ 磁盘余量足够

② 打分（软偏好，加权求和取最高）
   放置策略分（binpack 或 spread）      权重 100
   权重本地性分（该节点已缓存权重）      权重 ？  ← 见下
   当前负载分                            权重 ？
```

**不要写成字典序排序**（"权重已缓存 > 空闲 GPU 多 > 当前负载低"）。字典序意味着
第一个维度一旦有差异，后面的维度完全不起作用——"权重已缓存"这一条会压倒
"这台机器已经很挤了"。加权求和才能表达"本地性值多少"。

**权重本地性的权重要自己标定，别照抄。** GPUStack 给的是 5（放置分是 100），
即本地性只是平局打破器，几乎永远不会改变放置决策。但我们的权重在共享存储/
对象存储上，本地缓存命中省的是 2–5 分钟；如果这个时间对业务重要，
权重应当显著更高。**这是一个需要用 §12 的压测数据来定的参数，不是一个可以拍脑袋的常数。**

### 11.2.1 过滤器必须返回"为什么被过滤"

这一条看起来是体验问题，实际是运维成本问题。［GPUStack 验证］

每个过滤器不只返回通过的节点，还要返回**被过滤掉的原因**，
最终拼接进 `deployments.status_message`：

```
- Matched 4/7 workers by label selector.
- Worker node-03 filtered out: no backend version available for GPU device (cuda 12.4).
- The model requires approximately 164 GiB of VRAM. With --gpu-memory-utilization=0.9,
  all GPUs combined need at least 182 GiB, and each GPU needs 90% of allocatable VRAM.
- The largest available worker has 240 GiB allocatable VRAM, 2/8 of GPUs meet the
  VRAM utilization ratio, providing 43.2 GiB of effective VRAM.
```

自研调度器最容易省掉的就是这一段，然后界面上只有一个 `Pending`，
运维完全无从下手，只能去翻调度器日志。**这段文本的成本几乎为零
（过滤时顺手记一行），价值是把一类"需要开发介入"的工单降级成自助排查。**

### 11.3 GPU 分配记账：最容易出事的一处

K8s 有 device plugin 管这件事，裸机要自己记账。**记账错误的后果是两个容器抢同一张卡，第二个直接 CUDA OOM**，而且现象具有迷惑性——看起来像"显存不够"，实则是分配冲突。

> **［GPUStack 验证］先修正一个建模错误：`gpus.allocated_to` 不应该是一个被写入的状态字段。**
>
> `ARCHITECTURE.md` §4.4 现在的 `gpus(… status, allocated_to)` 隐含了
> "有人负责把这个字段写对"，于是就有了"写漏了/写重了"的可能——
> 也就有了漂移。正确的建模是：
>
> ```
> 已分配量 = f(deployments 表中当前的 部署→节点/卡 绑定关系)
> ```
>
> 即**它是一个从绑定关系派生的视图，不是一份独立的账**。
> 没有第二份账，就没有东西可漂。GPUStack 走过弯路后，把节点上报的
> `allocated` 字段直接标了 `@deprecated`，注释写明"服务端每次查询时
> 从当前 ModelInstance 绑定关系现算"——这正是 K8s 调度器计算
> `Node.Allocated` 的方式。
>
> `gpus` 表只保留**慢变的硬件事实**：`index / uuid / memory_total / model /
> interconnect / health`。`allocated_to` 删掉，改成查询时聚合的派生字段
> （或一个物化视图，如果聚合成为热点）。

由此，可分配量的计算是：

```
allocatable_vram[i] = max(gpu[i].total
                          − Σ(绑定到该卡的部署的 vram_claim)
                          − node.system_reserved_vram, 0)
```

**`system_reserved` 不能省**［GPUStack 验证］。不给系统留余量，节点会在
OOM killer 和调度器之间反复震荡：调度器认为还有空间，实际一起容器就被杀。

#### vram_claim 填什么：一个反直觉的关键点

**vLLM 的 `--gpu-memory-utilization`（默认 0.9）意味着它启动时会把
"卡总显存 × 0.9"整块吃掉建 KV Cache 池，不管模型实际多大。**
所以：

```
vram_claim[i] = gpu[i].memory_total × gpu_memory_utilization     ← 不是模型估算大小
```

用"模型估算大小"记账会得出"这张 80GB 卡上跑完 40GB 的模型还剩 40GB"，
然后调度器往上再放一个——第二个实例启动时会因为拿不到 90% 而失败，
或者两个都以奇怪的方式 OOM。

两条推论：

1. **一张卡默认放不下两个 vLLM 实例。** 要共卡必须显式给两边都降低 gmu，
   且两者之和 ≤ 1（还要留出系统预留）。这应当是部署配置里的显式选项，
   而不是让调度器"自动发现"。
2. **可分配量要同时校验绝对值与比例。** 只看"还剩多少 GB"会漏掉
   "还剩 20GB，但那是 80GB 卡的 25%，达不到 gmu=0.9"这种情况。
   校验条件是 `allocatable_vram[i] / total[i] ≥ gmu`。

多卡场景还有一条硬约束：**TP size 必须能整除模型的注意力头数**——
多模态模型还要**分别**检查语言塔与视觉塔的头数（视觉塔可能有 `num_dummy_heads`
需要加上）。这个检查放在调度阶段做，比让 vLLM 起来之后报错好得多。

#### 设备身份：卡该用什么来指称

这一小节修正一个贯穿全文的隐含假设——「GPU 用 index 指称」。［runtime 验证］

**① `index`（枚举序号）与设备节点号是两个不同的东西，混用会挂错卡。**

驱动给出的 minor number（`/dev/nvidia3` 里的 3）与 NVML 的枚举序号不一定相同。
GPUStack 早期把两者合并成一个字段，结果与 `CUDA_DEVICE_ORDER=PCI_BUS_ID`
的编号冲突（[gpustack#6041](https://github.com/gpustack/gpustack/issues/6041)），
后来拆开了：

| 用途 | 用哪个 |
|---|---|
| 调度、记账、`CUDA_VISIBLE_DEVICES` | 枚举序号 |
| 拼 `/dev/nvidia{N}` 这类设备节点路径 | minor number |

`gpus` 表要**同时存这两个字段**，且列名要能自解释（`enumeration_index` /
`device_minor`），不要叫 `index` 然后让每个使用者自己猜。

**② 跨检测唯一的身份是 UUID，不是 index。**

指标合并、对账、"这张卡还是不是上次那张"——**一律按 UUID 匹配**。
GPUStack 的注释写得很直接：*"a metrics list is joined by device identity and
never by index, as an index is not stable across a re-detection."*

`gpus` 表的业务主键应当是 `(node_id, uuid)`，index 只是一个属性。
配套两条：

- **同一个 UUID 被多张卡上报时，丢弃这条数据，不要猜。** 坏驱动会给每张卡
  报同一个 id，取任意一条都会把 A 卡的温度/显存写到 B 卡上。
  **宁可显示 N/A，不可显示错的值。**
- **一张卡掉线被跳过时，绝不能给存活的卡重新编号。** 压缩编号会让
  "卡 0 临时故障 → 卡 1 变成 0 号 → 卡 0 恢复后又变回去"，
  而数据库里记着的 `gpu_indices` 在这期间指向了另一张卡。
  **索引可以不连续、可以不从 0 开始，但绝不能因为别的卡的状态而移动。**

**③ 显存报驱动报的数，不做任何"修正"。**

GDDR 卡开 ECC 会吃掉约 1/16 容量，有些工具会把这部分加回去显示。
**不要在参与分配的字段上这么做**——`memory_total − memory_used` 必须
真的等于可用空间，加回不可达的容量会让每张开 ECC 的卡被超分。
界面若要显示标称容量，另开一个字段。

#### 检测采集的四条工程约束

这四条都是 G1 就要做对的，事后补代价很高。［runtime 验证］

**① 清单查询与用量查询必须拆开，频率与失败语义都不同。**

```
清单（慢变，进数据库）：uuid, name, minor, memory_total, compute_capability,
                        driver/cuda 版本, PCI 地址, NUMA 节点, 拓扑距离
用量（快变，进 Prometheus）：利用率, memory_used, 温度, 功耗, 健康状态
```

不只是"频率不同"这么简单——**NVIDIA 的 SM 利用率要靠 GPM 采样，
每张卡采两次样、中间 sleep 100ms**。8 卡机器一次采集就是 800ms，
而生成容器参数、算拓扑、做兼容性评估这些场景一个用量字段都不需要。
两者混在一个 `collect()` 里，代价会渗透到所有调用点。

**② 用量采集失败，不能连带丢掉清单。**

一张卡不管指标读没读到它都存在。把异常往上抛的后果是
**一台八卡健康的机器因为一次指标查询失败而上报零张卡**，
接着节点被判异常，接着上面的实例被迁走。

规则：**清单是硬事实，用量是软信息，后者失败只留空值。**
反过来说，节点健康度判定**不应该依赖 GPU 指标是否采到**。

**③ ⚠️ 健康检查会在坏卡上阻塞，必须带超时。**

读一张已经卡死的 GPU 的 ECC 计数器，**可能阻塞到驱动的 RPC 超时——
带 GSP 固件的卡上最长 45 秒**。如果状态采集是同步无超时的，
**一张坏卡就能让整个节点的心跳停掉**，然后节点被判 NOT_READY，
然后整机的健康实例全部被迁走——一张坏卡导致整机失守。

所以：**采集要有硬超时**（建议 5s），超时按"该卡健康状态未知"处理，
且**不能因此让整个节点的状态上报失败**。

**④ 健康判定：ECC 为 0 不代表卡是好的，且要 fail closed。**

两条容易漏的：

- **GSP 故障（Xid 119/154）时 ECC 计数器可读且为 0。** 必须额外查
  "是否需要 reset"的字段（NVML 的 `GPU_RECOVERY_ACTION` / `RESET_STATUS`），
  只看 ECC 会把一张已经废掉的卡当健康卡继续调度。
- **区分"查询失败"与"不支持"**：驱动报错（卡死后 RPC 超时返回 UNKNOWN）
  应当**判死**；而"这块卡不支持这个计数器"是判不了，应当保持原判定。
  两者都当成"不支持"，坏卡会一直被当好卡。

三条防线：

**① 单一真相源 + 分配加锁。** 派生的依据是 `deployments` 表。分配时在 Control 侧用数据库事务 + 行锁占位，拿到后再下发给 Agent，**绝不允许 Agent 自行决定用哪几张卡**——Agent 收到的是一个具体的 `gpu_indices` 列表，它只负责翻译成容器的设备挂载。同时 Agent 要**校验这几张卡是同型号**，混型号 TP 会以极难排查的方式失败。

**② 容器上打标签，让实际状态可反查。**

```
--label umaas.deployment_id=qwen3-72b-prod
--label umaas.gpu_indices=0,1,2,3
```

**③ 周期性对账（必须做）。** Agent 每分钟比对三方：

```
数据库记录的分配  ⟷  docker ps 的容器标签  ⟷  nvidia-smi 的实际进程占用
```

三者不一致时上报给 Control 并告警。常见的漂移来源：容器被人工 `docker rm`、进程 OOM 后容器退出但记录未清、Agent 重启期间发生的变更。**没有对账，记账迟早会漂**——这不是"可能"而是"一定"。

对账的两个方向都要做，且**都必须有创建时间宽限期**［GPUStack 验证］：

| 方向 | 处置 | 宽限期 |
|---|---|---|
| **有容器、无记录**（孤儿容器） | 删除容器 | **按容器创建时间，5 分钟** |
| **有记录、无容器** | 标 ERROR，交给重启逻辑 | 按记录创建时间，同上 |

**宽限期不是保守，是必须的**：容器刚被创建、Control 侧记录还没写完的那个窗口里，
不加宽限期会把正在创建的实例当孤儿杀掉——然后调谐循环再建一个，
再被杀掉，形成一个稳定的自毁循环。

第三条更重要的规则见 §11.5：**任何会摧毁存活工作负载的判定，
不能只依据本地缓存，必须先做一次权威回读。**

#### 把卡交给容器：两层变量，缺一不可

［runtime 验证］这里有一个**几乎所有自研方案都会踩的坑**：
"设备可见性"其实是**两层**，它们的失效条件不同。

| | 运行时可见设备 | 后端可见设备 |
|---|---|---|
| 变量 | `NVIDIA_VISIBLE_DEVICES` | `CUDA_VISIBLE_DEVICES` |
| 谁消费 | `nvidia-container-toolkit`（容器启动前挂设备节点） | CUDA 运行时（进程内过滤） |
| 作用 | 决定容器里**有哪些设备节点** | 决定应用**看到哪几张** |
| 何时失效 | **容器 `privileged` 时完全失效** | 应用自己覆盖时失效 |

**⚠️ `privileged` 容器能看到全机所有 GPU，`NVIDIA_VISIBLE_DEVICES` 形同虚设。**

因为 privileged 绕过了 container toolkit 的设备挂载控制，`/dev` 下所有设备节点
直接可见。此时唯一的限制手段是应用层的 `CUDA_VISIBLE_DEVICES`——
而容器里的进程只要 `unset` 它，就能用到全机的卡。

这对我们有两层影响：

- **记账层面**：一个行为异常的推理进程能占用未分配给它的卡，
  §11.3 的三方对账会报出"实际占用 ≠ 记录"，而排查方向会跑偏到调度器上。
- **安全层面**：多租户下这等于没有隔离。

**结论：不要默认 `privileged`。** 用显式设备挂载让隔离边界落在内核上：

```bash
# 推荐：显式挂设备节点，隔离由内核保证
--device /dev/nvidiactl --device /dev/nvidia-uvm --device /dev/nvidia-uvm-tools \
--device /dev/nvidia0 --device /dev/nvidia1 --device /dev/nvidia2 --device /dev/nvidia3
#         ↑ 这里用的是 device minor number，不是枚举序号（见上文 §设备身份 ①）

# 或者，非 privileged 下用 toolkit 的标准路径
--gpus '"device=GPU-1111-2222-...,GPU-3333-4444-..."'
#                ↑ ［runtime 验证］优先用 UUID 而不是索引，理由同上
```

若确因驱动要求必须 privileged，**必须同时显式设置 `CUDA_VISIBLE_DEVICES`**，
并在文档里写明"此时隔离是软的"。

#### ⚠️ `CUDA_DEVICE_ORDER=PCI_BUS_ID` 必须钉死

［runtime 验证］**CUDA 默认按性能启发式排序设备（`FASTEST_FIRST`），
而 NVML / `nvidia-smi` / 我们的检测按 PCI 总线序。在异构机器上两者编号不同。**

后果：调度器记账说"用 0、1 号卡"，容器里的 `torch.cuda.device(0)` 指向另一张。
显存对不上、TP 拓扑对不上，而且**没有任何报错**。

三条注入规则：

1. **只在容器能看到多于一张卡时注入**，单卡没有排序可言。
2. **`privileged` 或请求全部设备时一定注入**——这两种情况容器看得到所有卡。
   注意"请求全部"要**实际展开测量成几张**，不能当成一个 token 算 1 张。
3. **是默认值不是覆盖**：容器自己声明了 `CUDA_DEVICE_ORDER` 就用它的。

**"机器都是同型号卡就不用管"是错的**——今天同型号，加一台带不同代卡的机器
就会出问题，而症状是"某个部署显存莫名不够"。

#### TP 要的是"互联距离近"，不是"索引连续"

原文 §11.2 里"有足够**连续**空闲 GPU"这个表述是错的：
**4 张索引连续的卡完全可能分属两个 PCIe root complex。**

［runtime 验证］正确的建模是**距离矩阵 + 分级**：

| 级别 | 含义 |
|---:|---|
| 0 | 自己 |
| 5 | **高速互联**（NVLink / NVSwitch） |
| 10 | 经过至多一个 PCIe 桥 |
| 20 | 经过多个 PCIe 桥（不过 Host Bridge） |
| 30 | 经过 PCIe 及 Host Bridge（通常是 CPU） |
| 40 | 经过 PCIe 及 NUMA 节点间互联 |
| 50 | 跨 NUMA（QPI/UPI） |

选卡算法：**从每张空闲卡出发，按"由近到远"的顺序贪心取够 TP 需要的张数，
再比较各起点的总距离，取最小的那组。**

数据模型上，`nodes.interconnect` 这个单值字段不够用——它只能表达
"这台机器是 NVLink 还是 PCIe"，表达不了"0-3 号卡走 NVLink、4-7 号走 PCIe"
这种常见拓扑。应当改为在 `nodes` 上存一个**距离矩阵**（`topology jsonb`），
由 Agent 在注册与硬件变更时上报。

有一条捷径可以简化实现：**若某张卡有活跃的 NVLink，可以认为同机所有卡都通过
NVLink 互联**——这是 GPUStack 采用的近似，对绝大多数整机方案成立。

顺带：拿到 GPU 的 NUMA 节点后，可以进一步把容器的 CPU 绑到同一 NUMA
（`--cpuset-cpus` / `--cpuset-mems`），避免 host-to-device 拷贝跨 QPI。
**首版建议默认关闭**——这是压测能测出收益才该开的优化，且多卡跨 NUMA 时
约束会互相冲突。但字段先留好。

### 11.4 实例生命周期

vLLM 容器的实际启动参数（首版固定这一套，差异项由部署配置注入）：

```bash
docker run -d \
  --network host \                      # ★ 不做端口映射，见下
  --gpus '"device=GPU-1111-...,GPU-2222-..."' \  # ★ 用 UUID 而非索引（§11.3）
  --restart no \                        # ★ 不用 docker 自愈，见下
  # 注意：不加 --privileged。它会击穿设备隔离，见 §11.3「把卡交给容器」
  --label umaas.deployment_id=qwen3-72b-prod \
  --label umaas.gpu_uuids=GPU-1111-...,GPU-2222-... \
  --shm-size=16g \                      # TP 多进程通信需要，默认 64MB 会失败
  -v /data/models:/models:ro \          # 本地权重缓存，只读挂载
  -v /var/lib/umaas/cache/vllm:/cache \ # ★ 编译缓存持久化
  -e VLLM_CACHE_ROOT=/cache \
  -e CUDA_DEVICE_ORDER=PCI_BUS_ID \     # ★ 必须钉死，否则容器内外编号可能不同
  -e OMP_NUM_THREADS=1 \
  -e NCCL_SOCKET_IFNAME==bond0 \        # ★ 前导 '=' 是精确匹配语法，不是笔误
  -e GLOO_SOCKET_IFNAME=bond0 \
  -e VLLM_HOST_IP=10.0.1.23 \
  vllm/vllm-openai:${engine_version} \  # ★ 版本来自部署配置，不是常量（§7.1）
  --model /models/Qwen3-72B-Instruct \
  --served-model-name qwen3-72b \       # ★ 平台强制注入，与上游模型名同源（§7）
  --host 10.0.1.23 --port ${assigned_port} \   # ★ 端口动态分配，见下
  --tensor-parallel-size 4 \
  --max-model-len 32768 \               # ★ 有平台默认上限，不跟随模型（§3）
  --gpu-memory-utilization 0.90 \       # ★ 这个值决定记账口径（§11.3）
  --enable-prefix-caching \
  --disable-log-requests                # 生产环境，否则日志量爆炸
```

**八个容易踩的点**（后六条来自对参考实现的复核）：

- **不加 `--privileged`，并显式钉死 `CUDA_DEVICE_ORDER=PCI_BUS_ID`。**
  两条的理由都在 §11.3「把卡交给容器」，是本方案里最容易静默出错的两处。
- **设备用 UUID 指称，不用索引。** 索引跨检测不稳定，UUID 是唯一稳定身份。


- **`--shm-size` 必须显式设置**。Docker 默认 64MB，而 TP>1 时 vLLM 的多进程通信走共享内存，会直接启动失败且报错信息不直观。
- **`--disable-log-requests`**。默认会把每个请求的完整 prompt 打进日志，高 QPS 下磁盘会被打满，且**包含用户数据**，有合规风险。
- **不要开 `--ipc=host`。**（除非挂了需要 CUDA-IPC 的共享 KV Cache 服务）
  **Docker 在 host IPC 模式下会忽略 `--shm-size`**——你以为设了 16g，
  实际用的是宿主机的 `/dev/shm`，大小完全不受控。而且 K8s 的 PodSecurity
  baseline 直接拒绝 hostIPC，将来若迁移会卡住。
- **`--restart no` + 由调谐循环重启。** 用 Docker 的 `restart: always` 看起来省事，
  但它会绕过控制面：容器自己重启成功了，而 Control 里的记录还是 ERROR，
  或者反过来。重启应当是**状态机的一次显式转移**，带指数退避
  （`min(10 × 2^(n-1), 300)` 秒）与 `restart_count` 计数，超过阈值就停下来告警，
  而不是无限重启一个必然失败的配置。
- **`--network host` + 端口动态分配。** 固定 `-p 8101:8000` 在单机跑多实例时
  必然冲突。要从一个端口段里分配，且**分配要加锁**（同节点并发创建时会撞）。
  vLLM 分布式还要额外预留 3 个端口（DP RPC 的 ZMQ 端口、PyTorch 分布式的
  TCPStore 端口、`VLLM_PORT`），并且**要把 DP master 端口往后的 10 个端口
  整段拉黑**——vLLM 会在这个区间内自行占用。
- **多节点必须钉住网卡：`NCCL_SOCKET_IFNAME` / `GLOO_SOCKET_IFNAME`。**
  不设的话 NCCL 会自己挑网卡，在有多张网卡（管理网 + 存储网 + 计算网）的
  机器上极大概率挑错，表现为**初始化时静默挂死，没有任何错误信息**，
  是多机推理最经典的故障。注意 NCCL 的语法：`=bond0` 表示精确匹配，
  `bond0` 表示前缀匹配（会同时匹配 `bond0`、`bond01`…）。

**状态机**：

```
creating → loading → healthy → draining → stopped
              │         │          │
              └─failed  └─unhealthy└─(在途请求结束)
```

- `loading` 阶段 `/health` 会持续失败 3–5 分钟，**这是正常的**。健康检查必须区分"还在加载"与"真的坏了"——用启动宽限期（grace period）而非直接判死。前端方案的部署预检清单里已经写明这一点。
- `draining`：先从路由摘除（Control 更新渠道状态），等在途请求结束或超时，再 `docker stop`。drain 超时取 `max_output_tokens ÷ 最慢生成速度`，通常 2–5 分钟。
- **`docker stop` 的默认 10 秒宽限不够**，要显式给 `--time`，否则会在 drain 完成前强杀。

#### 健康检查分三层，且真实流量可以豁免主动探针

［GPUStack 验证］

| 层 | 探测 | 判定 |
|---|---|---|
| **① 容器状态** | 容器运行时的 state | `PENDING`/`INITIALIZING` → 还在起，**跳过后续检查**，不算失败 |
| **② HTTP 探针** | `GET /v1/models` | 进程活着且 HTTP 栈就绪 |
| **③ 真实推理探针** | `POST /v1/chat/completions`，`max_tokens=1`，**用真实模型名** | 端到端可用，挡住 §7 的 404 陷阱 |

第一层不能省：没有它，加载中的实例会被判为 unhealthy 并触发重启，
而重启后又要重新加载，永远起不来。

第三层要按模型类别选端点：embedding 打 `/v1/embeddings`，
reranker 打 `/v1/rerank`，图像/语音类直接跳过（它们的最小请求代价太高）。

**一个很划算的优化：如果最近一个探测周期内有过成功的真实推理请求，
就跳过这一轮主动探针。** 真实流量本身就是最好的健康证明。
实现上让数据面在响应成功时回调一下 Agent 记个时间戳即可。
这样忙碌的实例不会被探针额外打扰（探针会占一个调度槽位），
而空闲实例仍然被持续验证。

#### 日志：带重启序号，且要能断流续接

日志文件名带 `restart_count`（`{deployment_id}.{restart_count}.log`），
**重启后还能看上一次的失败日志**——这是排查"为什么一直重启"的唯一线索，
覆盖写就等于把证据销毁了。

拉容器日志流的线程要能处理 EOF 后重连（容器重启、运行时抖动）：
重连时运行时会 replay 历史日志，需要用**已写入的最后几行做锚点**跳过重复部分。
用一行做锚点会误匹配（日志里有重复行很常见），取 5 行的窗口。

#### 从 Docker API 读状态：四个解析陷阱

Agent 要把 Docker 的容器状态翻译成我们的状态机。这一步有四个坑［runtime 验证］：

**① `restarting` 状态的容器已经填好了上次的退出码。** 崩溃循环的容器在两次尝试
之间就停在 `restarting`，而 `State.ExitCode` 里已经是上次失败的码——
**这正是要诊断的那个值**。只查 `exited` 会漏掉最需要诊断的情况。
携带退出码的状态集合是 `{exited, dead, restarting}`。

**② Docker 未设置的时间戳是 Go 零值 `0001-01-01T00:00:00Z`，不是缺 key。**
所以 `attrs["State"]["FinishedAt"]` 永远有值，`if v == ""` 判不出"没结束过"。
要显式判前缀。

**③ 同样是非零退出，有无重启策略决定判定不同。** 有重启策略 → `UNHEALTHY`
（它自己会起来）；没有 → `FAILED`（终态）。我们已定 `--restart no`（§11.4），
所以恒走后者，但解析代码不要写死——人工起的容器可能带策略。

**④ 退出信息要结构化保存，不要只存一句 message。**

```
deployment_exits  deployment_id, container_id, exit_code, reason,
                  message, started_at, finished_at, restart_count
```

`reason` 的取值是有限集合（`OOMKilled` / `Error` / `ImagePullBackOff` / 信号量），
把它做成字段而不是塞进 message，界面才能按"因 OOM 失败的部署"筛选，
告警才能区分"配置错了"和"显存不够"。**`OOMKilled` 尤其要能一眼看出来**——
它意味着 §11.3 的显存估算或 gmu 设置有问题，是一个需要回头改参数的信号，
而不是一次偶发失败。

#### 一个更可靠的 `loading` 判定：init 容器

§11.4 现在用"启动宽限期"来区分"还在加载"与"真的坏了"。
这个方案的固有问题是：**宽限期设长了故障发现慢，设短了正常启动被误杀**，
而 145GB 模型的加载时间本身波动很大（取决于缓存命中、磁盘负载）。

［runtime 验证］更可靠的做法是用 **init 容器**：把"校验权重完整性 / 预热页缓存"
这类前置工作放进一个先跑的容器，主容器等它退出后才启动。
于是：

```
init 容器在跑        → loading（确定事实，不是猜测）
init 容器退出码 != 0 → failed（且 reason 明确）
主容器在跑但未就绪   → 仍需宽限期，但窗口小得多（只剩引擎自身初始化）
```

裸 Docker 上实现 init 容器需要 Agent 自己编排（起 A、等 A 退出、再起 B），
不复杂但要注意幂等（§11.5）。**首版可以先用宽限期**，
把这条记作 G3 之后的优化项——前提是别把"一个部署 = 一个容器"写死进数据模型。

### 11.5 调谐循环

没有 K8s 的 controller，就自己写一个。Control 侧维护期望状态，Agent 上报实际状态，差异触发动作：

```
期望 = deployments 表中 status=running 的实例
实际 = 各 Agent 上报的容器状态
差集处理：
  期望有、实际无  → 创建（或标记失败，若重试超限）
  期望无、实际有  → 回收（孤儿容器，通常是 Control 重启前的残留）
  两者都有但状态不符 → 按状态机推进
```

**关键：动作必须幂等。** 网络分区时 Control 可能重复下发同一条指令，Agent 要能识别"这个 deployment_id 的容器已经在跑了"而不是再起一个——容器标签正是为此。

**要限制并发动作数**。同时创建 5 个实例会让权重加载抢满磁盘 IO 与网络带宽，反而每个都变慢。首版限制为**每节点同时只做一个创建动作**。

#### 11.5.1 三层触发，缺一不可

「每 15 秒全量对比一次」这个最朴素的写法有两个问题：正常情况下延迟高（平均 7.5 秒），
异常情况下又不够（watch 断连时它是唯一的兜底，但 15 秒扫全量在规模上来后很贵）。

［GPUStack 验证］正确的结构是**三层叠加**：

| 层 | 周期 | 作用 | 代价 |
|---|---|---|---|
| **事件驱动** | 毫秒 | 快路径，99% 的情况靠它 | 低 |
| **周期全扫** | 分钟级（如 180s） | 兜底事件丢失、进程重启、watch 断连 | 中，但频率低 |
| **权威回读** | 仅在"要做破坏性动作"时 | 防缓存不一致导致误杀 | 高，但极少触发 |

只有第一层的系统在 watch 断连时会静默失效；只有第二层的系统延迟高且贵；
**少了第三层的系统会周期性地误杀健康实例**——下面单独说这一条。

#### 11.5.2 破坏性动作前必须权威回读

这是自研调谐循环最容易出的事故，也是最难复现的：

```
Agent 侧的实例列表来自 watch 缓存。
watch 重连时，客户端会先清空缓存、再接收全量快照。
在这个窗口里读缓存，得到的是「空的但看起来是权威的」。
于是 「本地在跑的 − 缓存里属于我的」= 「全部在跑的」
→ 把所有健康实例都当成陈旧的杀掉。
```

［GPUStack 验证］的解法：

```
① 先快照本地状态，再拉列表        ← 顺序反了会和"新分配"竞态
② 用缓存算出「疑似要回收」的集合   ← 常态是空集，零成本
③ 若非空 → 用一次绕过缓存、不分页的权威查询重算这个集合
④ 只对复核后仍在集合里的执行拆除
```

常态下（没有要回收的）完全不查库；只有真要动手时才付一次查询代价。

**推广成一条通则：读可以用缓存，写和删必须基于权威回读。**
这条同样适用于 §11.3 的 GPU 记账对账、§3.4 的缩容选择。

#### 11.5.3 只留一条拆除路径

收到删除事件时**不要立刻拆除**，交给周期性回收去做。理由有两条：

1. 回收逻辑本来就必须能处理"watch 断连期间丢失的删除事件"，
   所以它必然存在，也必然能覆盖这个场景。
2. 两条路径同时拆除同一个容器，就会有两个并发调用方竞争
   `docker rm`——一个成功一个报"容器不存在"，而后者会被当成异常上报。

**事件是加速器，不是唯一入口。** 每一类状态变更都应当有且只有一个执行者，
事件的作用是让它更早被触发。

#### 11.5.4 工作队列的语义要求

调谐循环的队列不能是一个裸的 channel，它至少要满足五条：

| 保证 | 为什么 |
|---|---|
| **同 key 串行** | 取出的 key 在 `done()` 之前不能再被取出，否则两个 goroutine 同时改一个部署 |
| **删除事件优先且黏性** | 插队到头部，且**不被后到的非删除事件覆盖**（否则删除会丢） |
| **延迟重入（`AddAfter`）** | 控制器要"过 N 秒再看一眼"时，**不能靠写库触发事件**——那会形成"写自己的状态 → 触发事件 → 再次入队"的自激轮询 |
| **按 key 指数退避** | 一个反复失败的部署不能把队列刷爆 |
| **去抖窗口 + 最大等待** | 合并高频更新，同时用最大等待上限防止连续更新流饿死处理 |

Go 生态里 `client-go` 的 `workqueue` 包已经把这五条都实现了，**直接用它**，
不要自己写一个 channel + map。这里的每一条都对应一类真实故障。

第三条尤其值得强调：**"控制器写自己的 status 来触发下一轮观察"是一个
必然踩的坑**。它看起来很自然（反正要更新状态），但结果是每个进行中的部署
都变成一个持续的写库轮询，规模上来后数据库先扛不住。

#### 11.5.5 Leader 丢失时直接退出进程

Control 的调谐循环必须是单 Leader 的（多个 Leader 会同时对同一个部署下发指令）。
续租失败时**不要尝试优雅停止各个循环**，直接 `os.Exit(1)` 让进程管理器拉起为 standby。

［GPUStack 验证］理由写在它的注释里：优雅停止意味着要证明每一个控制器循环
都能被可靠取消，而这很难证明；进程退出是唯一能证明的。
**脑裂的代价（两个 Leader 同时调度）远高于一次重启。**

### 11.6 与 admin 五页的对应

| admin 页面 | 后端支撑 | 阶段 |
|---|---|---|
| 集群总览 | Agent 上报的节点/GPU 拓扑 + `gpus` 表 | G1 |
| GPU 监控 | DCGM + vLLM `/metrics` → Prometheus | G1 |
| 模型仓库 | 对象存储拉取 + 节点本地缓存 + SHA256 校验 | G2 |
| 部署实例 | §11.4 生命周期 + §11.5 调谐 + Docker 日志流 | G3 |
| 容量评估 | **调度器 dry-run**（见下），非独立计算 | G3 |
| 性能压测 | Agent 执行并发爬坡，回传结果（§12） | G7 |

**容量评估页不要写第二套计算逻辑。**［GPUStack 验证］「这个模型能不能在当前集群跑起来、
需要几张卡」这个问题，**答案就是调度器跑一遍的结果**——把 §11.2 的过滤+打分
以只读方式执行，返回候选与被过滤原因，不落库。

前端已有的 `lib/capacity` 只能作为**交互期的即时预估**（用户还在填表时给个大概），
点"检查兼容性"时必须走后端的 dry-run。两套逻辑必然分叉，分叉之后的典型症状是
"界面说能跑，实际调度不上去"，而排查方向会完全跑偏到集群资源上。

dry-run 端点要注意两点：带结果缓存（key 取 模型规格 + 节点状态的哈希，
且**显式排除利用率、温度这类高频抖动字段**，否则缓存永远不命中），
以及对上游元数据查询限流（拉模型 config 会打 HuggingFace 的接口）。

### 11.7 什么时候该重新考虑 K8s

裸机方案的适用边界要写明，避免将来在错误的路上走太远。出现以下任一情况，重估：

- 节点数超过 **30 台**——自研调度的边界情况会开始密集出现
- 需要**多区域/多集群**——跨集群调度自己写代价很高
- 需要**混部**（GPU 节点同时跑其他工作负载）——资源隔离与优先级抢占是 K8s 的强项
- 团队已经在维护 K8s——那时复用比自研便宜

在此之前，裸机 + Docker 的简单性是实打实的收益：一台机器装 Docker 和 nvidia-container-toolkit 就能加入集群，排查问题只需要 `docker logs` 和 `nvidia-smi`。

## 12. 压测与容量基准（G7 的设计前置）

G7 排在最后，但**它的输出是 §2 评分权重、§3 容量公式、§4 单位成本的共同输入**。
如果基准测出来是错的，前面所有的判断都建立在错的数字上。这一节写清楚
"什么样的压测结论是可信的"。

### 12.1 三种负载形态、两种负载轴

```
负载轴：  fixed_rate（开环，按 rps 施压，不管服务端跟不跟得上）
         concurrency（闭环，固定在途请求数）
负载形态：single（单点）| stages（逐档跑）| auto_tune（自适应爬坡找拐点）
```

**两个轴测的是不同的东西**：开环测"服务端在给定压力下会劣化到什么程度"，
闭环测"给定并发下的稳定表现"。自建容量规划要的是前者的拐点，
而 SLO 承诺要的是后者的分位数。

［GPUStack 验证］一个小而实的教训：**负载轴要做成枚举类型，不要用字符串。**
它们踩过一次——某处拼写错误让标着 `concurrency` 的任务实际按 rate 扫描执行，
静默错了很久，因为两种模式的结果曲线看起来都"合理"。

### 12.2 ⚠️ TPOT 有两个定义，用错误差可达 40%

**这是本节最重要的一条，也是最容易在事后才发现的错误。**［GPUStack 验证］

「每个输出 token 的时间」有两种算法，很多工具同时报这两个值：

```
① 纯解码间隔（inter-token latency）
   (last_token_ts − first_token_ts) / (tokens − 1)
   ← 这才是 vLLM / genai-perf 语境下的 TPOT

② 端到端摊销（time per output token）
   (last_token_ts − request_start) / tokens
   ← 把 TTFT 和排队等待摊进了解码时间
```

用 ② 当 TPOT，误差是 `TTFT / (n × TPOT)`：

| 输出长度 | 误差量级 |
|---|---|
| 128 token | ~5% |
| **16 token** | **~40%** |

而且**误差随负载增大**（负载高 → TTFT 涨 → 摊进去的更多），
恰好在"决定容量拐点"的那个区间最不准。

两条实施要求：

- **SLO 阈值一律绑定 ①**，并在指标名上把两者区分开（§6 的表已经分开列了）。
- **但要保留 ② 作为回退**：服务端不做增量流式（一个 chunk 吐完整个输出，
  低负载与短输出时很常见）时，首末 token 时间戳相同，① 会报 0。
  **0 会通过任何阈值**——不回退则该点被判失败，爬坡会在第一个点就被卡死；
  直接采信 0 则等于废除了这条 SLO。回退到 ② 是唯一正确的处理。

### 12.3 结论必须区分"拐点"与"扫描上限"

一个孤零零的"最大并发 = 64"是没有意义的：它可能是测出来的拐点，
也可能只是扫描范围的上限（再往上没测）。这两者对容量规划的含义完全相反。

［GPUStack 验证］所以压测结果要同时记录**两类信息**，且不可互相推导：

- **停止原因（由执行器写入）**：`capacity_plateau`（吞吐平了）/
  `upper_bound`（撞到扫描上限）/ `budget_points` / `budget_seconds`（预算用尽）。
  **几种终止会留下完全一样的曲线，下游无法反推**，所以必须由执行器记录。
- **曲线本身**：用来判断结论可信度、给出改进建议。

判定用的阈值（每个都要写清楚为什么是这个数）：

| 常量 | 参考值 | 含义 |
|---|---|---|
| 最低成功率 | 0.95 | 低于此说明该点已过载，数据不可信 |
| 平台期容差 | 0.05 | 最后一档吞吐涨幅 <5% → 曲线已平，不是范围不够 |
| SLO 余量比 | 0.70 | 只用掉 70% 预算 → 停止原因不是延迟，别归因给 SLO |
| 跟得上比例 | 0.80 | 实际 rps < 80% 施压 rps → 服务端明显跟不上 |

并且当**最优点落在测量区间的端点上时，结论要显式标注为"下界"而不是"拐点"**，
界面上要提示"建议扩大扫描范围重测"。

### 12.4 压测环境的两条纪律

- **数据集要每次换种子。** 同一份合成 prompt 跑两次，第二次会命中前缀缓存，
  吞吐虚高。要测缓存收益就单独设计对照实验，不要让它污染基线。
- **压测容器与推理实例同样受 §11.3 的记账约束。** 压测客户端如果跑在
  GPU 节点上，它占用的 CPU 与网络会影响被测实例——首版建议压测客户端
  跑在独立节点，并在结果里记录它的位置。

| GPUStack 的做法 | 不采纳的理由 |

| 网关侧静态权重 + 状态码 fallback | 自建过载表现为排队而非错误码，永不触发（§2） |

| Docker 上的 pause 容器 | 首版单容器部署不需要（但别把"一个部署 = 一个容器"写死进数据模型） |
| autoheal sidecar 重启不健康容器 | 与 §11.5.3「只留一条拆除路径」冲突——控制面已在做重启 |
| 健康检查默认关闭 | 它默认关是因为它是个库、不知道调用方的超时预算。我们是自己的 Agent，应当**开启但带超时** |
| 手写 ctypes 驱动绑定 | Go 侧有官方 `go-nvml`，不需要自己写。但**同样不要 shell out `nvidia-smi`**——CLI 拿不到 NVML 一半的字段且输出格式跨版本会变 |

### 13.3 对 `ARCHITECTURE.md` 的修改请求

本次修订引出以下对 §4.4 数据模型的改动，需要在那份文档里同步：

1. **`gpus` 表去掉 `allocated_to`**，改为查询时从 `deployments` 的绑定关系聚合。
   保留 `status` 但语义收窄为硬件健康（healthy/degraded/fault），不表达分配状态。
2. **`gpus` 表的设备标识要拆成三个字段**（§11.3 设备身份）：
   ```
   uuid                 业务主键的一部分，(node_id, uuid) 唯一；跨检测唯一稳定的身份
   enumeration_index    调度/记账/CUDA_VISIBLE_DEVICES 用
   device_minor         拼 /dev/nvidia{N} 设备节点路径用
   ```
   现在只有一个 `index` 字段，会被两种用途混用。
3. **`nodes.interconnect` 单值字段改为 `topology jsonb`**（距离矩阵 + 每卡 NUMA 节点）。
   单值表达不了"0-3 号卡走 NVLink、4-7 号走 PCIe"这种常见拓扑。
4. **新增 `model_file_replicas` 表**（§5.1），`local_models` 保留为
   "模型的权威副本元数据"，两者是一对多。
5. `deployments` 表补三个字段：`image_name`、`engine_version`、
   `detected_engine_version`（§7.1、§6.1）。
6. **新增 `deployment_exits` 表**（§11.4 解析陷阱 ④）：
   `deployment_id, container_id, exit_code, reason, message, started_at, finished_at, restart_count`。
   `reason` 独立成字段，界面才能按 `OOMKilled` 筛选。
