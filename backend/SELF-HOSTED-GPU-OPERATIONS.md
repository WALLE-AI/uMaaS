# 自建 GPU 集群运营方案

> 状态：待评审 · 2026-09-06
> 前提：已确认运营自有 GPU 集群（`SERVICE-DECOMPOSITION.md` §11-C）
> 归属：`SERVICE-DECOMPOSITION.md` §3-④ Infra Agent 的展开
> **本文是混合供给路由、容量管理、自建成本核算的真相源**

---

## 1. 自建与云端是两种经济体，不是两个渠道

最容易犯的错是把自建 vLLM 当成"又一个渠道"，塞进和 OpenAI 同一套渠道表就完事。它们的经济特征几乎处处相反：

| | 云端 API | 自建 GPU |
|---|---|---|
| 成本结构 | **按量**，不用不花钱 | **固定**，GPU 买了/租了就在计费 |
| 边际成本 | 每个 token 都要付钱 | **接近 0**（电费可忽略不计） |
| 闲置代价 | 无 | **全额浪费** |
| 容量 | 弹性（受限于对方配额） | **刚性**，由显存与 `max_num_seqs` 决定 |
| 过载表现 | 429 拒绝 | **排队**，TTFT 线性劣化但不拒绝 |
| 扩容时间 | 毫秒（换个渠道） | **分钟级**（加载 145GB 权重） |
| 失败切换 | 换渠道重试 | 同左，但换回来要等实例恢复 |

这些差异导出三条完全不同的运营目标：

- 对云端：**尽量少用**（每次调用都是钱）
- 对自建：**尽量用满**（闲置就是纯亏）
- 二者之间：**自建优先，饱和后平滑溢出到云端**

**GPU 利用率是自建供给唯一重要的运营指标。** 一张 H100 每月成本固定，利用率 20% 和 80% 的单位 token 成本差 4 倍。

## 2. 混合供给的路由：不写死规则，把特征喂进评分

直觉做法是写一条规则：「优先自建，自建满了走云端」。**不要这么做**——它需要人工定义"满了"的阈值，而这个阈值随模型、并发、上下文长度变化；而且一旦自建实例劣化（比如某张卡降频），硬规则会固执地继续往上打。

正确做法是**复用 `UNIFIED-PROVIDER-INTERFACE.md` §5.5 已有的评分引擎**，只是把自建的真实特征喂进去，让"优先自建"和"饱和溢出"成为**涌现结果**而非硬编码：

```
effective = (w_rel·reliability + w_speed·speed + w_intel·intelligence)
            × headroomFactor × rateLimitFactor
            × costFactor            ← 新增维度
```

三处对接：

**① `costFactor` 让自建自然胜出。** 自建的边际成本≈0，成本因子取满分；云端按实际单价归一化。在任何成本敏感的策略下，自建自动排在前面——不需要任何"优先自建"的 if 语句。

**② 队列深度进 `speed` 因子，让饱和自动溢出。** 自建实例过载的表现不是 429 而是排队，TTFT 线性上升。把实例的**排队深度与近期 TTFT** 喂进 speed 维度后，随着队列变长，speed 分下降，effective 分随之下降，云端渠道自然反超——**溢出是连续的，不是阈值触发的开关**。

这一点很关键：阈值式溢出会在临界点附近抖动（一会儿走自建一会儿走云端），而连续评分不会。

**③ `headroomFactor` 用显存水位而非配额。** 云端渠道的 headroom 是"剩余免费额度"，自建是"剩余 KV Cache 空间"。同一个 ramp 函数，喂不同的量。显存逼近上限时实例即将拒绝新请求，提前压低分数比等它报错更好。

**必须保留一条硬规则**：某些模型只在自建有（私有微调模型），某些只在云端有。这是**可行集约束**，在评分之前完成过滤，不参与打分。

## 3. 容量管理：时间常数决定了必须预测而非响应

云端渠道的容量调整是毫秒级的——切个渠道就行。自建不是：

```
新增一个 Qwen3-72B 实例的时间构成
├── 调度到有空闲 GPU 的节点        秒级
├── 拉取镜像（若无缓存）           1–3 分钟
├── 从共享存储加载 145GB 权重      2–5 分钟   ← 主要成本
├── CUDA graph 捕获与预热          30–60 秒
└── 健康检查通过、纳入路由         10 秒
                                   ─────────
                                   合计 3–8 分钟
```

**结论：自建容量必须预测性扩容，不能等过载了再加。** 等 TTFT 已经劣化再扩，用户已经难受了 5 分钟以上。

三层应对：

| 层次 | 时间尺度 | 手段 |
|---|---|---|
| **瞬时** | 秒 | 溢出到云端（§2 的连续评分自动完成） |
| **短期** | 分钟 | 预热池：保留 1–2 个已加载权重的空闲实例待命 |
| **中长期** | 小时/天 | 按历史流量曲线预排程（工作日白天扩、夜间缩） |

**预热池的成本要算明白**：一个待命的 H100 实例每小时都在烧钱。它值不值，取决于「溢出到云端的成本」是否高于「预热池的闲置成本」。这是可计算的：

```
预热池划算的条件：
  预期溢出 token 量 × 云端单价  >  预热实例小时成本 × 待命小时数
```

这个判断应该由数据驱动、定期复核，而不是拍脑袋定一个"永远留 2 个"。

**缩容比扩容更需要小心**：正在处理请求的实例不能直接杀。必须先从路由中摘除（停止接新请求），等在途请求自然结束（或超时上限），再回收。这个过程要有明确的 drain 超时——通常取 `max_output_tokens / 最慢生成速度`。

## 4. 自建模型的成本核算：摊销值，不是定价

`frontend/admin` 的模型分析页显示 `$/1M tokens`，用于云端与自建对比。**自建的这个数字有本质不同，必须标注清楚，否则会误导决策。**

```
自建单位成本 = (GPU 小时成本 × 实例运行小时数 + 存储与网络分摊)
              ÷ 该时段实际产出的 token 数
```

关键性质：**它是利用率的函数，不是常数。**

| GPU 利用率 | H100 月成本 | 月产出 tokens | 单位成本 |
|---|---|---|---|
| 20% | $2,000 | 0.9B | **$2.22 / 1M** |
| 50% | $2,000 | 2.2B | $0.91 / 1M |
| 80% | $2,000 | 3.5B | **$0.57 / 1M** |

（数量级示意，实际取决于模型与序列长度）

**利用率 20% 时，自建可能比云端 API 还贵。** 这是"自建一定更便宜"这个直觉最常翻车的地方。

因此在 admin 的分析页上，自建模型的成本必须：

1. **标注为「摊销成本」**，与云端的「供应商计价」区分显示
2. **附带当期利用率**，让读者知道这个数字的前提
3. **给出盈亏平衡利用率**——低于这条线，自建不如直接买 API

`ARCHITECTURE.md` §4.3 的 `cost_usd_micro` 字段对自建请求填的是**摊销值**，需要一个后台任务按周期回填（请求发生时还不知道当期最终利用率）。这意味着自建请求的成本数字**在当期结束前是估算值**，UI 上要能区分。

## 5. 权重存储与分发

145GB 一个模型，多节点部署同一模型时如何分发，是自建绕不开的工程问题。

| 方案 | 首次加载 | 后续加载 | 运维 |
|---|---|---|---|
| **共享存储（NFS/CephFS）** | 慢（网络带宽瓶颈） | 慢，每次都走网络 | 简单 |
| **对象存储 + 节点本地缓存** ✅ | 慢（一次） | **快（本地 SSD）** | 中等，要管缓存淘汰 |
| 每节点独立下载 | 慢 | 快 | 浪费带宽与磁盘 |

推荐**对象存储（S3/OSS）为权威副本 + 节点本地 SSD 缓存**：

- 权重不可变（同一 revision 内容固定），缓存不需要失效逻辑，只需要 LRU 淘汰
- 节点本地缓存命中时，加载时间从"网络传 145GB"降到"本地 SSD 读 145GB"，差一个数量级
- 缓存淘汰按「最近未使用 + 当前无实例引用」，正在被实例使用的权重不能淘汰

**磁盘容量是硬约束**：一个节点缓存 4–5 个大模型就要 1TB 级别。`frontend/admin` 的模型仓库页已有磁盘水位显示，后端要提供每节点的缓存占用与命中率。

## 6. 可观测：两层指标，缺一不可

`ARCHITECTURE.md` §4.4 已定「GPU 实时指标不入库，从 Prometheus 查」。这里补充**必须同时采集两层**：

**第一层：硬件（DCGM Exporter）**

利用率、显存、温度、功耗、SM 时钟、ECC 单/双位错误、XID、NVLink 带宽、降频原因。

**第二层：推理引擎（vLLM / SGLang 自身的 `/metrics`）**

这一层比硬件层更贴近用户体验，却经常被忽略：

| 指标 | 为什么必须有 |
|---|---|
| `num_requests_running` / `num_requests_waiting` | **队列深度**，§2 的溢出判断直接依赖它 |
| `gpu_cache_usage_perc` | KV Cache 水位，比显存总量更能预测"还能接多少并发" |
| `time_to_first_token_seconds` | 引擎侧 TTFT，与网关侧对比可分离出网络耗时 |
| `time_per_output_token_seconds` | 生成速度劣化的早期信号 |
| `num_preemptions` | **抢占次数**。KV Cache 不足时 vLLM 会抢占已有序列，这是过载的明确信号 |

**只看 GPU 利用率会误判**：利用率 95% 可能是健康的满负荷，也可能是在反复抢占重算。`num_preemptions` 才能区分这两种情况。

## 7. 与统一接口方案的衔接

自建模型走 `UNIFIED-PROVIDER-INTERFACE.md` §4.4 的 `openai_compatible` 驱动（vLLM/SGLang 都提供 OpenAI 兼容接口），**零协议适配代码**。但有三处差异要在 `ProviderProfile` 里表达：

```go
Quirks{
    // vLLM 的 max_model_len 在启动时固定，超过会直接报错而非截断
    MaxModelLenFixed: true,
    // 自建实例通常不做认证，或用简单的 bearer
    AuthScheme: AuthSchemeNone,
    // 支持 vLLM 特有的采样参数（top_k、repetition_penalty 等）
    ExtraSamplingParams: []string{"top_k", "repetition_penalty", "min_p"},
}
```

**模型名映射要注意**：vLLM 启动时用 `--served-model-name` 指定对外名字，若不指定则用权重路径。`channel_models.upstream_model_name` 必须与之一致，这是自建部署最常见的低级错误之一——部署成功、健康检查通过，但一调用就 404 model not found。**部署预检清单里应当包含"以 `--served-model-name` 实际调用一次"这一项**，而不只是检查进程存活。

## 8. Infra Agent 的职责边界

| 职责 | 说明 |
|---|---|
| GPU 指标采集 | 抓 DCGM + 引擎 metrics，暴露给 Prometheus |
| 实例生命周期 | 创建、健康检查、drain、销毁；上报状态给 Control |
| 权重管理 | 从对象存储拉取到本地缓存、校验、LRU 淘汰 |
| 容量决策执行 | **执行**扩缩容指令，不做决策 |
| 压测执行 | 跑并发爬坡，回传结果 |

**明确不属于 Infra Agent 的**：

- **扩缩容决策**（属于 Control，因为决策要看全局流量与成本，Agent 只看本集群）
- **路由**（属于 Gateway）
- **计费**（属于 Control）

这条边界的意义：Agent 可以是"哑"的执行器，逻辑集中在 Control。多集群时 Agent 可以有多个实例，而决策仍然唯一。

## 9. 实施顺序

对应 `ARCHITECTURE.md` §9 的 B7，可细分为：

| 步骤 | 内容 | 判据 |
|---|---|---|
| **G1** | Agent 骨架 + GPU/引擎双层指标采集 | admin 的 GPU 监控页接真实数据 |
| **G2** | 权重拉取 + 本地缓存 + 校验 | 模型仓库页可用；缓存命中率可见 |
| **G3** | 实例生命周期（创建/健康检查/drain/销毁） | 部署实例页可用；drain 不中断在途请求 |
| **G4** | 自建接入路由（`costFactor` + 队列深度进评分） | **自建优先且饱和自动溢出，无硬编码规则** |
| **G5** | 成本核算与摊销回填 | 分析页显示摊销成本 + 当期利用率 + 盈亏平衡点 |
| **G6** | 预热池与预测性扩缩容 | 流量高峰前自动扩容，无人工介入 |
| **G7** | 压测执行 | 压测页接真实数据，结果回写容量基准 |

**G4 是价值拐点**：在此之前自建集群只是"被管理的资源"，之后才真正成为供给。建议 G1–G3 之后先做 G4，把 G5–G7 排在后面。

## 10. 需要确认的问题

**A. 编排底座：K8s 还是裸机？** 这直接决定 Agent 的实现方式。

- **K8s + GPU Operator**：实例即 Pod，扩缩容、调度、健康检查复用 K8s 原语，Agent 主要是 Operator/Controller。代价是要维护 K8s
- **裸机 + systemd/Docker**：Agent 要自己实现调度与生命周期管理，工作量显著更大，但没有 K8s 的运维负担

前端方案 §11-C 与 `ARCHITECTURE.md` §10-C 都问过这个问题，仍未确认。**G3 之前必须定下来**。

**B. GPU 是自有机房还是云上 GPU 实例？** 影响两处：云上实例可以按需创建销毁（弹性更好但按小时计费），自有机房是纯固定成本（更该追求高利用率）。§3 的预热池经济性计算依赖这个前提。

**C. 推理引擎：vLLM 单选还是 vLLM + SGLang 双选？** 双选意味着两套部署参数、两套 metrics 格式、两套 quirks。建议**首版只上 vLLM**，SGLang 等有明确性能收益证据再加。

**D. 是否需要多集群/多区域？** 若需要，Agent 要支持多实例部署，且路由要感知区域亲和性（跨区调用的网络延迟会吃掉自建的延迟优势）。首版建议单集群。
