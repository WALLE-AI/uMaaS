# 服务拆分方案

> 状态：待评审 · 2026-09-06
> 议题：backend 是否采用微服务架构，如何拆
> 归属：`ARCHITECTURE.md` §8 部署形态的展开
> **本文是服务边界、服务间通信、部署拓扑的真相源**

---

## 1. 唯一还站得住的冲突

原本这里列了三条冲突（SQLite、不引 Redis、私有化单机）。**云上部署确定后，前两条已解除**——`ARCHITECTURE.md` §7 已改为单一 Postgres，Redis 也升为必需组件。私有化单机不再是必须交付项。

于是拆分的自由度大幅提高，但**有一条冲突是架构性的，不会因为换数据库而消失**：

> **计费必须强一致，而分布式事务是微服务最大的成本中心。**
>
> 一次推理请求要：查配额 → 预扣 → 转发 → 结算。若"配额服务"和"网关服务"分离，这条链路就跨越了服务边界。要么引入 Saga/TCC（复杂度陡增），要么接受最终一致（意味着**可以超额，产生坏账**）。`ARCHITECTURE.md` §6.3 已明确：配额扣减宁可慢也不能超额。

这条冲突决定了本文最重要的一条边界：**计费不跨服务边界**。配额裁决用 Redis 原子操作 + Postgres 对账，全部发生在一个服务内部。

> 这条边界内部的完整设计（价目模型、预扣—结算—释放、余额与信用额度、对账参数）
> 见 [`BILLING-AND-PRICING.md`](./BILLING-AND-PRICING.md)。该文 §5 的全部流程都发生在单一服务内，
> 与本条边界一致；`QuotaService` 接口（§4）的语义以那里为准，本文只给形状。

另有两条不是冲突但要算清的成本：

| 成本 | 说明 |
|---|---|
| **热路径多一跳** | Gateway 拆出去后，查模型/渠道要跨进程。不做本地缓存，这一跳会直接体现在 TTFT 上（见 §6） |
| **两套拓扑的测试** | 同一份代码跑单进程与多进程，事务语义存在隐藏差异（见 §4） |

**所以结论不是"要不要微服务"，而是"哪些边界值得付这个代价"。** 答案不是全拆，也不是不拆。

## 2. 拆分原则：按变化率 / 性能特征 / 故障域，不按领域名词

最常见的拆分错误是按名词切：`user-service`、`model-service`、`billing-service`、`order-service`。这种切法的问题是**业务操作横跨所有名词**——一次推理要用到 user（鉴权）、model（路由）、billing（扣费）、log（记录），于是每个请求都变成 4 次 RPC + 一个分布式事务。拆完比不拆更慢、更脆。

正确的判据是三条，满足**至少两条**才值得独立成服务：

| 判据 | 含义 |
|---|---|
| **性能特征不同** | 扩容依据不一样（连接数 vs CPU vs IO），放一起会互相拖累 |
| **故障域应隔离** | A 挂了不该影响 B，且 B 的可用性要求明显更高 |
| **变化率不同** | 发布节奏差异大，高频改动的模块不该逼着稳定模块跟着重启 |

按这三条筛，本系统真正的服务边界是 **4 个**，不是 8 个也不是 15 个。

## 3. 服务边界

```
                          ┌──────────────────┐
   SDK / Agent  ─────────▶│  ① Gateway       │  推理数据平面
   (OpenAI 兼容)          │  高并发 · 长连接  │  按在途连接数扩容
                          └────────┬─────────┘
                                   │ gRPC（热路径）
                          ┌────────▼─────────┐
   web / admin  ─────────▶│  ② Control API   │  控制平面
                          │  CRUD · 会话      │  按 CPU 扩容
                          └────────┬─────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              │                    │                    │
     ┌────────▼────────┐  ┌────────▼────────┐  ┌───────▼────────┐
     │ ③ Worker        │  │  共享存储        │  │ ④ Infra Agent  │
     │ 用量聚合/目录同步 │  │  Postgres        │  │ GPU/部署编排    │
     │ 压测/下载        │  │                  │  │ 需特权 · 近机器  │
     └─────────────────┘  └──────────────────┘  └────────────────┘
```

### ① Gateway（推理数据平面）—— 最值得拆，优先级最高

三条判据全中：

- **性能特征**：长连接、SSE 流式、单请求几十秒。扩容看在途连接数而非 CPU。与控制平面放一起会把连接池吃干净（`ARCHITECTURE.md` §1 已述）
- **故障域**：它挂了 = 用户无法调用模型，是最高等级故障。控制平面挂了只是管理界面不可用，用户的推理请求照常
- **变化率**：适配器和 quirks 是**高频改动区**（上游行为会漂移，见统一接口方案 §2.3），而它又是最不能出事的服务

**这是唯一一个"不拆是错的"服务。** 即便其他全部保持单体，它也应该独立。

### ② Control API（控制平面）—— 保持单体，不再细拆

`/api/v1/*` 的 21 个端点 + `/admin/*`。**内部按模块划分，但不拆成多个服务。**

理由：catalog / auth / billing / analytics 之间共享大量数据且有事务需求。把它们拆开，收益是"团队可以并行"，代价是分布式事务 + N 倍的部署运维。以当前规模，代价远大于收益。

**内部用模块化单体的纪律约束**（见 §5），保留将来拆分的缝。

### ③ Worker（后台任务）—— 值得拆，中等优先级

用量聚合、目录同步、模型权重下载、压测执行、健康探针。

- **性能特征**：批处理，CPU/IO 密集且波动大。跑一次全量聚合可能吃满 CPU 几分钟——放在 API 进程里会拖垮在线请求的 p99
- **故障域**：Worker 挂了不影响在线服务，只是聚合数据延迟
- 模型下载单个任务持续几十分钟、占用大量磁盘 IO，与 API 进程的资源争抢是实打实的

### ④ Infra Agent（自建模型集群编排）—— 必需服务

GPU 指标采集、部署实例生命周期、模型权重拉取、压测执行。

> **一个必须澄清的区分**：「后端服务部署在云上」与「是否管理自有 GPU 集群」是**两件独立的事**。
> 前者已定（本文 §1）；后者由产品决定——`frontend/admin` 有完整的私有化部署五页
> （集群总览 / 容量评估 / 模型仓库 / 部署实例 / GPU 监控），统一接口方案也把
> 自建 vLLM/SGLang 列为供给来源之一。**只要要跑自建模型，这个服务就需要**，
> 无论那些 GPU 是租的云实例还是自有机房。
>
> 它唯一不需要的场景是：平台完全只做上游 API 的聚合转发，不自建任何推理能力。

- **故障域**：它要跟 K8s API / Docker socket / GPU 驱动交互，**需要特权**。这类权限不该给面向公网的 API 进程
- **部署位置不同**：它必须运行在能访问 GPU 节点的网络位置，而 Control API 可以在任何地方
- **变化率**：编排逻辑与 GPU 驱动/推理引擎版本强相关，改动频率高于控制平面

### 明确不拆的

| 候选 | 为什么不拆 |
|---|---|
| auth / user | 与几乎所有操作耦合，拆了每个请求多一跳 |
| billing / quota | **计费要强一致**，拆开就要分布式事务或接受坏账 |
| catalog / model | 读多写少，缓存友好；拆了只增加延迟 |
| analytics 查询 | 与 catalog 共享模型元数据，查询要 join |

## 4. 关键设计：同一份代码，单进程与多进程都能跑

这是让「现在不拆」与「将来能拆」**同时成立**的技术核心。

做法是**所有跨服务调用都走接口，而接口有两种实现**：

```go
// 领域层只认接口，不知道对方是本地对象还是远程服务
type QuotaService interface {
    Check(ctx context.Context, req QuotaRequest) (*QuotaVerdict, error)
    PreConsume(ctx context.Context, req PreConsumeRequest) (*Reservation, error)
    Settle(ctx context.Context, res *Reservation, actual Usage) error
}

// 实现一：进程内直调。零序列化、零网络、可参与同一个数据库事务
type localQuotaService struct{ store domain.Store }

// 实现二：gRPC 客户端。跨进程，带超时/重试/熔断
type remoteQuotaService struct{ client quotapb.QuotaClient }
```

启动时按配置装配：

```go
func buildServices(cfg Config) *Services {
    if cfg.Topology == TopologyMonolith {
        return &Services{ Quota: newLocalQuota(store), Catalog: newLocalCatalog(store), … }
    }
    return &Services{ Quota: newRemoteQuota(cfg.QuotaAddr), Catalog: newRemoteCatalog(…), … }
}
```

**收益**：本地开发与早期生产跑单进程装配（一个进程、启动快、调试简单）；规模上来后切多进程装配，各服务独立扩容。**业务代码一行不改，拆分是配置决策而非重构。**

云上部署确定后，这一层的价值从"让私有化单机成立"变成了**"让拆分可以推迟到真正需要时"**——先用单体跑，等触发条件出现再拆，而不是一开始就承担分布式系统的全部成本。

**代价要说清楚**，这不是免费的：

1. **接口必须是"可远程化"的形状**。参数与返回值要能序列化，不能传 `*sql.Tx`、不能传闭包、不能依赖调用方的内存状态。这个约束从第一天就要守，事后改代价极大。
2. **本地实现能参与同一事务，远程实现不能**。这是最危险的隐藏差异——单机跑得好好的事务语义，切多进程后静默变成最终一致。**必须在接口契约里显式声明哪些操作要求事务原子性**，并对这些操作禁止远程实现（编译期或启动期拒绝）。
3. **错误语义要统一**。本地实现返回 `domain.ErrNotFound`，远程要把 gRPC status 映射回同一个错误，否则上层的错误处理会在两种形态下表现不同。

## 5. 模块化单体的纪律：拆分缝怎么留

不拆的部分要用纪律保持"随时可拆"，否则将来想拆也拆不动。四条硬规则：

**规则一：模块之间只通过接口通信，禁止跨模块直接访问对方的 store。**

```
✅ billing.Service 调用 catalog.Service.GetModel(id)
❌ billing 内部直接 SELECT * FROM models
```

违反这条，将来拆分时会发现数据边界早已糊成一团。Go 可以用 `internal/` 嵌套目录在**编译期**强制：`internal/catalog/internal/store/` 只有 catalog 包能导入。

**规则二：跨模块调用不共享事务。**

模块内可以用事务，跨模块不行。这样"本地实现"和"远程实现"的事务语义一致，切换拓扑不会出现语义漂移。代价是某些跨模块操作要用补偿而非回滚——**这个代价现在付，比拆分时付便宜得多**。

**规则三：每个模块有独立的表前缀与所有权。**

一张表只有一个模块能写。其他模块要改数据，走该模块的接口。这是将来"每服务一库"的前提。

**规则四：CI 检查依赖方向。**

用 `go list -deps` 或 `depguard` 在 CI 里断言模块依赖图是 DAG，不存在环。**依赖成环是拆分的头号杀手**，且它总是悄悄形成的。

## 6. 服务间通信

| 场景 | 方式 | 理由 |
|---|---|---|
| Gateway → Control（查模型/渠道/配额） | **gRPC** | 热路径，每次推理都要调。需要低延迟、二进制编码、连接复用、流式支持 |
| Control → Worker（派发任务） | **数据库队列**（river / 表 + 轮询） | 已有 Postgres，不引入 MQ。任务需要持久化与重试 |
| Worker/Infra → Control（上报状态） | gRPC 或 HTTP | 低频 |
| Infra Agent → Gateway（自建模型上下线） | 通过 Control 中转 | 避免 Agent 直连 Gateway，减少拓扑耦合 |
| Control ↔ Infra Agent | **Agent 主动外联的 gRPC 双向流** | 机房在 NAT 后无公网入站地址；不必在机房防火墙开入站端口。详见自建 GPU 方案 §10.5 |

**不引入消息队列作为必需组件。** Postgres 的 `SKIP LOCKED` 做任务队列在我们的量级完全够用（river 就是这么实现的），少一个中间件就少一份运维。真到了 MQ 才能解决的规模，再引入不迟。

**热路径必须有本地缓存。** Gateway 每次推理都要查模型元数据和渠道配置——这些是**慢变数据**，必须在 Gateway 进程内缓存（秒级 TTL + Control 主动失效通知）。否则拆分带来的网络往返会直接体现在 TTFT 上。这一条不做，拆分就是纯亏。

## 7. 三种部署拓扑

同一份代码，三种装配：

| | 开发 / 早期生产 | 云上标准 | 云上大规模 |
|---|---|---|---|
| **拓扑** | `monolith` | `split` | `split` + 独立用量存储 |
| **进程** | 1 | Gateway ×N、Control ×2、Worker ×1 | 各自独立扩容 |
| **数据库** | Postgres（compose / 托管） | Supabase / RDS | + ClickHouse 承接 `request_logs` |
| **服务通信** | 进程内直调 | gRPC | gRPC |
| **状态共享** | Redis（单实例） | Redis | Redis 集群 |
| **Infra Agent** | 同进程模块 | **每 GPU 节点一个**（机房与云上均有） | 同左 |
| **Gateway 部署位置** | 本机 | **仅云上一套**（机房与云同城，见自建方案 §10.5） | 同左，按需加副本 |
| **运维复杂度** | compose 起 3 个容器 | 3 类 Deployment | 加 HPA、独立存储 |

**关键**：`monolith` 不再是"必须交付的产品形态"（私有化单机已取消），但仍应保持可用——它是**本地开发的默认拓扑**，也是"拆分尚未触发时"的生产形态。CI 至少要保证它能启动并跑通冒烟测试，否则装配层会悄悄腐化，等到想拆时才发现远程实现从来没被验证过。

## 8. 拆分的触发条件

不要因为"微服务是先进架构"而拆。每个服务的独立部署都要满足一个**可观测的触发条件**：

| 服务 | 触发条件 |
|---|---|
| **Gateway** | 立即拆（不依赖规模，性能特征与故障域决定） |
| **Worker** | 聚合任务开始影响 API 的 p99；或单个任务运行超过 5 分钟 |
| **Infra Agent** | **已确定需要**（运营自有 GPU 集群）。因需特权且部署位置不同，必拆 |
| Control 再细拆 | **暂不考虑**。除非出现明确的团队边界冲突，且能接受分布式事务成本 |

**反向条件同样重要**：如果拆分后 6 个月内没有出现"独立扩容/独立发布"的实际需求，说明拆错了，应该合回去。合并的成本远低于继续维护一个没有收益的分布式系统。

## 9. 拆分带来的新问题清单

诚实列出微服务必然引入的成本，这些都要有对应方案，否则拆分就是把复杂度从代码转移到运维：

| 问题 | 应对 |
|---|---|
| **分布式追踪** | OpenTelemetry，`request_id` 贯穿全链路（契约已要求返回 `request_id`，正好复用） |
| **配置一致性** | 单一配置源 + 启动期校验；服务间的共享常量（如模型 ID 格式）放共享包 |
| **版本兼容** | gRPC 接口只增不改；跨服务发布时旧版 Gateway 必须能与新版 Control 共存 |
| **本地开发体验** | 默认 `monolith` 拓扑，开发者跑一个进程即可，不需要起全套服务 |
| **集成测试** | 两种拓扑都要测。`monolith` 跑全量，`split` 跑关键路径 |
| **故障排查** | 日志必须带 `request_id` + `service_name`；错误跨服务传递时保留原始 code |
| **数据一致性** | 跨服务操作用补偿，不用分布式事务；强一致操作（计费）不跨服务边界 |

## 10. 建议的推进路径

**不建议一步到位。** 按以下顺序，每步都可独立验证价值：

| 阶段 | 动作 | 验证 |
|---|---|---|
| **S0** | 模块化单体 + §5 的四条纪律 + CI 依赖检查 | 依赖图是 DAG；模块间无直接 store 访问 |
| **S1** | 引入拓扑装配层（本地/远程双实现），但**只运行 monolith** | 接口形状可远程化；切换拓扑无需改业务代码 |
| **S2** | 拆出 **Gateway**，gRPC + 本地缓存 | Gateway 独立扩容；TTFT 未因拆分劣化 |
| **S3** | 拆出 **Worker** | 聚合任务不再影响 API p99 |
| **S4** | 按需拆 **Infra Agent**（有自建 GPU 时） | 特权隔离；Agent 挂掉不影响推理 |

**S0 和 S1 是无论如何都该做的**——它们不引入分布式系统的任何成本，却保留了全部拆分的可能性。如果最终发现不需要拆，这两步的投入也不浪费（模块化本身就是好设计）。

**S2 之前保持 `monolith` 为默认拓扑**：本地开发与早期生产都走它，装配层只在 CI 里验证远程实现可用。

## 11. 需要确认的问题

**A. 拆分的真实驱动是什么？** 这决定了拆到什么程度：

- 如果是**性能/扩容**：拆 Gateway 就够了，S2 止步
- 如果是**团队并行**：需要知道团队规模与划分方式。少于 3 个后端的团队做微服务通常是净亏损
- 如果是**故障隔离**：Gateway + Worker 足够
- 如果是**技术栈异构**（比如某模块想用 Rust 写）：那是拆分的强理由，但要指明是哪个模块

> ~~**B. 私有化单机形态是否仍是必须交付项？**~~ **已定（2026-09-06）**：云服务部署，
> SQLite 仅为临时测试方案。已连带解除本文原 §1 的前两条冲突，拓扑表与装配层动机相应更新。

> ~~**C. 是否运营自有 GPU 集群？**~~ **已定（2026-09-06）**：需要。Infra Agent 由"可选"升为
> **必需服务**，`frontend/admin` 的私有化部署五页有后端支撑，自建 vLLM/SGLang 成为一等供给来源。
> 由此产生的容量、成本、路由问题见 [`SELF-HOSTED-GPU-OPERATIONS.md`](./SELF-HOSTED-GPU-OPERATIONS.md)。

> ~~**C. 是否已有 K8s 平台？**~~ **已定**：**不用 K8s**，裸机 + Docker。
> 这意味着拆分后的服务编排也走 docker-compose（平台服务是固定拓扑，正合适），
> 服务发现由 Control 的配置下发承担，不需要注册中心。
> 代价是没有 HPA——`split` 拓扑下 Gateway 的扩容首版为人工/脚本触发。

**D. Control API 内部是否有团队边界？** 如果 catalog / billing / analytics 由不同团队负责且冲突频繁，可以考虑进一步拆分——但必须先接受"计费不跨服务边界"这条底线，否则会掉进分布式事务的坑。
